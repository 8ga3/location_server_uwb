# マルチアンカー UWB 測位システム 設計メモ

M5Stamp-UWB (QM33120) を用いた DS-TWR 測距を、単一ペアからマルチアンカー測位へ拡張するための設計検討。
対象は Atom S3 / Atom S3 Lite / Atom Lite + M5Stamp-UWB。ライブラリは `m5stack/M5Stamp-UWB`。

- 作成日: 2026-09-21
- 想定用途: ローバー型ラジコンの自己位置推定
- 現状: タグ 1 台 ⇔ アンカー 1 台の DS-TWR が動作済み

---

## 1. システム構成

```text
  [アンカー 0..N-1]        [タグ (ローバー搭載)]        [サーバー]
   M5Stamp-UWB             M5Stamp-UWB + Atom            アンカー座標表
   固定設置                 + フライトコントローラ          を保持
        |                          |                          |
        +----- UWB DS-TWR ---------+                          |
                                   +------- Wi-Fi ------------+
                                     起動時に座標表を取得
```

### 役割分担

| 要素 | 責務 |
| --- | --- |
| アンカー | UWB responder。固有 ID のみ保持。座標は持たない |
| タグ | UWB initiator。全アンカーを巡回測距 → 三辺測量で自己位置を算出 |
| サーバー | アンカー座標表とバイアス補正値を保持。タグへ配布 |
| FC (フライトコントローラ) | IMU による姿勢・慣性。Atom 内蔵 IMU は使用しない |

**測位計算はタグ側の Atom 内で実行する。** サーバーからは座標表を起動時に 1 度取得するだけで、
以降の測位ループはオフラインで完結する。Wi-Fi が切れても測位は継続できる。

## 2. アンカーアドレスの割り当て

### 2.1 制約

ライブラリの `respondDSRange()` は、受信フレームの `dst != responderAddress` の場合そのフレームを破棄する
(`.pio/libdeps/*/M5Stamp_UWB/src/M5Stamp_UWB.cpp` の該当箇所)。ブロードキャスト受信には対応していない。
したがって**アンカーごとにユニークな `responderAddress` が必須**である。

また Poll フレームの宛先はタグ側が指定するため、**タグは各アンカーのアドレスを事前に知っている必要がある**。
このため「MAC アドレス下位 16bit を自動採番」のような方式は単体では成立しない (タグが知り得ない)。

### 2.2 採用方針 (実装済み)

16bit ショートアドレスを役割ごとの範囲に分け、**アドレスそのものを機体の ID として直接持たせる**。
別のオフセット値を介さないため、ログに出るアドレスと設定した ID が常に一致する。

```text
panId             = 0xDECA              (全機共通)
タグ              = 0x0001..0x00FF      (initiatorAddress)
アンカー          = 0x0100..0xFFFE      (responderAddress)
```

- タグは当面 1 台だが、下り TDoA (`downlink-tdoa-design.md`) では多数のタグが前提になるため 255 台分を予約しておく
- `0xFFFF` は 802.15.4 のブロードキャストアドレスなので、アンカーの上限は `0xFFFE`
- アドレスの上位側を見るだけでタグかアンカーかが判別でき、ID 空間が衝突しない

この設計により以下が成立する。

- タグはアンカー ID の一覧を順に叩くだけで全アンカーを巡回できる
- 巡回が実質的に TDMA として機能し、アンカー間の衝突が発生しない
- ライブラリの responder は受信フレームの `dst` と `panId` しか照合しない (`src` は見ない) ため、
  アンカー側はタグ ID を知らなくてよい。応答は常に Poll の送信元へ返される

タグが巡回するアンカー ID の一覧は、**起動時に測位サーバーから設置座標とあわせて取得する** (第 7 節 /
[server-design.md](server-design.md) 5.1)。取得した構成は NVS へキャッシュし、サーバーへ届かないときは
キャッシュで動作する。キャッシュも無い場合は巡回先が決まらないため測距を開始しない。

### 2.3 ID の設定方法 (実装済み)

ソースコードを直接書き換えて台数分ビルドする方式は避ける。以下を採用する。

#### 採用方式: NVS (Preferences) 保存 + 起動時のシリアル入力

当初検討した「ボタン長押しでインクリメント」方式は、画面のない Atom Lite / AtomS3 Lite では
現在値を提示できず (LED 1 個で 4 台以上の ID を表現できない)、採番 UI として成立しないため採用しない。
ボタンは**設定モードへ入るトリガのみ**に使う。

- 全機に同一ファームウェアをフラッシュする
- NVS namespace `uwb` / key `id` に 16bit で保存。再フラッシュしても保持される (`erase_flash` を実行しない限り)
- 起動時、ID が未設定 (または役割の範囲外) ならシリアル入力を待つ。**10 進数**で入力し、
  範囲外や数字以外は `ID_INPUT,result=ERR` を返して再要求する
- 入力待ちの表示: 画面のある AtomS3 は LCD に `SET ID` と入力中の値、画面のない Lite 系は
  **LED マゼンタ点灯**。マゼンタは通常動作の RED / YELLOW / GREEN と重ならないので一目で判別できる
- 電源投入またはリセット直後に本体ボタンが押されていれば、設定済みでも設定モードへ入る (現場での振り直し)
- 起動時ログに `DEVICE_ID,role=...,id=...,source=nvs|serial` を必ず出力する

シリアル入力を待つ間は UWB を初期化しない。ID が決まる前に電波を出さないためである。

実装は両プロジェクトの `src/device_id.h` (同一内容のコピー)。ボタンのピンは LED と同じ理由で
`getBoard()` ではなくビルドターゲットから決める (AtomS3 系 G41 / Atom Lite G39)。

## 3. 測位の原理と必要台数

### 3.1 測距と測位の区別

DS-TWR が返すのは距離スカラーのみである。座標を得るには、**既知のアンカー座標**と組み合わせた三辺測量が必要になる。
アンカー配置が事前に既知であることは、計算をどこで行うかに関わらず前提となる。

### 3.2 座標系

相対座標でよく、絶対座標や方位は不要。アンカー 0 を原点、アンカー 0→1 方向を X 軸に取るのが定石。
ただし**スケールは実寸**が必要なので、アンカー間距離は実測値を用いる。

### 3.3 必要台数 (測位側)

DS-TWR は真の距離を返すため、時刻バイアスの未知数が不要。

- **2D 測位 (高さ既知): 未知数 2 → 3 台で一意、4 台で冗長 1**
- 3D 測位: 未知数 3 → 4 台で一意、5 台で冗長 1

重要なのは「設置台数」ではなく「**その瞬間に見えている台数**」である。4 台設置でも遮蔽により 3 台しか届かなければ
冗長ゼロ、2 台なら測位不能となる。ローバーの場合、車体自身や障害物による遮蔽が発生しうる。

### 3.4 配置 (GDOP)

- アンカーを一直線または一直線に近い形に配置すると、解が極端に不安定になる
- 測距誤差 10cm が位置誤差 1m 級に増幅されうる
- 4 台なら**正方形に近い配置**とし、タグ (ローバー) は 4 台が作る四角形の**内側**を走行させる
- 四角形の外に出ると精度が急落する

### 3.5 初期方針

**2D 測位・アンカー 4 台・座標は手測り**から開始する。

- 高さは全アンカー同一とし、2D 問題として解く
- ローバーは地上を走るため高さ方向の変動が小さく、2D で十分
- 自動推定 (self-survey) は後述するが、初期段階では手測りで確実に動かす

## 4. アンカー座標の自動推定 (self-survey) — 将来の拡張

手測りが動作した後の拡張として検討する。

### 4.1 ライブラリ側の実現可能性 (確認済み)

- `receiveFrame()` はアドレスフィルタを一切行わない。`src` / `dst` は結果として返るのみ。
  → 任意の制御メッセージの受信に使える
- `M5Stamp_UWBFrameConfig.dst` のデフォルトは `0xFFFF` (ブロードキャスト)
- `requestDSRange()` / `respondDSRange()` は毎回 config を引数で受け取り、内部に役割状態を持たない。
  → **同一機体で呼び分けるだけで initiator / responder を切り替えられる**

### 4.2 手順

#### フェーズ 0: サーベイモード起動

通常の responder ループを抜けて survey モードへ入る。トリガはボタン長押しまたはシリアルコマンド。

#### フェーズ 1: 相互測距

1. マスター 1 台 (アンカー 0 で固定してよい) がブロードキャストで `ROUND=i` を告知する
2. `anchorId == i` の機体が initiator となり、`responderAddress` を書き換えながら j = 0..N-1 (j≠i) を順に `requestDSRange()`
3. **それ以外の全機体は `respondDSRange()` を回しっぱなしにする。** 自分宛でないフレームは dst 不一致で自動的に破棄されるため、調停は不要
4. ラウンド完了後 `DONE` をブロードキャストし、マスターが `ROUND=i+1` へ進める

両方向 (i→j と j→i) を測定して平均すると、アンテナ遅延の非対称性が均される。
各ペア 20 回程度測定し**中央値**を採ってマルチパス外れ値を除去する。

#### フェーズ 2: 距離行列の集約

各 initiator が `D,i=0,j=3,mm=4213` 形式でシリアル出力する。マスター 1 台を PC に接続し、
ブロードキャストで報告を集めて一括出力する方式でもよい。

#### フェーズ 3: 座標計算 (PC 上で実行。ESP32 で行う必要はない)

1 回限りの作業なので Python が適している。

古典的 MDS で初期解を得る。

1. 対称化: `d_ij = (d_ij + d_ji) / 2` として N×N 距離行列 D を構成
2. 二重中心化: `J = I - (1/N) * ones((N,N))` として `B = -0.5 * J @ (D**2) @ J`
3. B を固有分解し、固有値の大きい順に k 個 (2D なら k=2) を取る
4. `X = V_k @ sqrt(diag(lambda_k))` が初期座標 (N×k)

次に非線形最小二乗で精密化する (`scipy.optimize.least_squares`)。

残差を `r_ij = ||x_i - x_j|| + b - d_ij` と定義して最小化する。
`b` はアンテナ遅延由来の共通オフセットであり、**未知数に加えて同時推定する**のが要点。
ここで得た `b` はタグ測位時の距離にも同様に効くため、補正値として保存しサーバー側で配布する。

#### フェーズ 4: ゲージ固定

MDS の解は並進・回転・鏡映が自由なので固定する (2D の場合)。

1. 平行移動: アンカー 0 を原点へ移す
2. 回転: アンカー 1 が +X 軸上に来るよう全体を回転
3. 鏡映: アンカー 2 の y が正になるよう、必要なら y の符号を反転

これで数値的には一意に定まる。ただし**実世界のどちら向きかは決まらない**。
「アンカー 2 は実際に 0→1 方向から見て左か右か」の 1bit だけは人が目視で判断する必要がある。ここは自動化できない。

#### フェーズ 5: 検証

- **残差 RMS**: 数 cm〜10cm 程度なら妥当。それ以上なら遮蔽や NLOS を疑う
- **スケール照合**: 1〜2 辺をメジャーで実測して比較する。系統的にずれていればバイアス `b` の推定が効いていない
- **固有値チェック**: 2D なら λ3 が λ1, λ2 に対して十分小さいこと。大きければ配置が平面でない

### 4.3 self-survey に必要な台数

2D で自由度を数える。

- 未知数: N 点 × 2 = `2N`、ゲージ固定で −3 (並進 2 + 回転 1)、バイアス b を +1 → **2N − 2**
- 観測数: ペア数 = **N(N−1)/2** (両方向は平均するため 1 ペア 1 拘束)

| N | 観測数 | 有効未知数 | 冗長度 |
| --- | --- | --- | --- |
| 3 | 3 | 4 | 解けない (b を諦めれば辛うじて一意) |
| 4 | 6 | 6 | **0 — 一意だが自己検証不能** |
| 5 | 10 | 8 | 2 |
| 6 | 15 | 10 | 5 |

**N=4 では残差が常に 0 になる。** 測距が 1 本ずれていても、それを吸収する形に座標が動くだけなので、
残差からは異常を検出できない。

注意: 各ペアを 20 回測定しても幾何的な冗長性は増えない。繰り返しはノイズ平均化にしか効かず、
形の拘束数は**ペア数のみ**で決まる。

結論として、**self-survey を検証込みで運用するには 5 台以上が必要**。
4 台で self-survey を試すこと自体は構わないが、必ず手測り値と突き合わせること。

### 4.4 高さ (Z) の扱い

**アンカーを全て同じ高さに設置すると、相互測距だけでは Z が決まらない** (同一平面の退化)。
「2D は自動推定、高さは手測り」を推奨する。3D を自動化する場合は、数台を意図的に異なる高さに設置する必要がある。

### 4.5 運用上の注意

- survey 中の見通しは必須。遮蔽されたペアは系統的に長い距離として出る。残差の大きいペアは除外して再計算する
- アンカーを移設するたびに survey を再実行する。ボタン起動にしておくと現場で回せる

## 5. 測位レートの検討

目標: **最低 10Hz、可能なら 30Hz**。

### 5.1 時間予算

現状の `M5Stamp_UWBDSRangeConfig` (`src/main.cpp` の `initUwb()`) で DS-TWR 1 回を積算する。
uus (UWB microsecond) ≈ 1.0256µs。

| 項目 | 設定値 | 実時間 |
| --- | --- | --- |
| `responseTxDelayUus` | 3000 uus | 3.08ms |
| `finalTxDelayUus` | 1800 uus | 1.85ms |
| `resultRxAfterFinalTxDelayUus` | 500 uus | 0.51ms |
| フレーム空中時間 (4 本) | — | 約 1ms |
| **合計 (支配項)** | | **約 6.5ms / 測距** |

4 アンカー巡回で 26ms ≈ 38Hz。数値上は 30Hz に乗るが余裕はない。

### 5.2 削減すべきパラメータ

#### `resultRepeatCount = 3` + `resultRepeatGapMs = 3`

アンカーが Result フレームを 3 回送信する設定。タグは 1 回目で受信できれば抜けられるが、
**アンカー側は送り切るまで次の Poll を受けられない**ため、1 台あたり +6ms のビジー時間が生じる。
4 台巡回では無視できない。信頼性が確認できているなら `resultRepeatCount = 1` に落とす。ここが最大の削減余地。

#### `hostTimeoutMs = 100` — 実用上の最大リスク

1 台が応答しなかった瞬間、そのサイクルに 100ms を消費する。30Hz (33ms) どころか 10Hz も割り込む。
遮蔽は必ず発生するため、これは「もし」ではなく「いつ」の問題である。
`hostTimeoutMs` は 1 測距の想定時間 + マージン (15〜20ms 程度) まで下げる。`rxTimeoutUus` も同様に見直す。

#### シリアルログ

115200bps = 約 87µs/byte。現状の `DS_RESP_STAT` 行は 100 文字を超えており、**1 行で 8.7ms** を消費する。
30Hz (33ms 周期) で毎サイクル出力すると、それだけで予算の 1/4 が消える。

- 対策 1: `monitor_speed` を 921600 に引き上げる (1.1ms に短縮)
- 対策 2: 測位ループ中はログを間引く (現状の `LOG_INTERVAL` による間引きは正しい方向)

### 5.3 SPI 速度

Atom Lite (classic ESP32) は `config.spi_fast_hz = 8000000` に落としている
(全信号が GPIO マトリクス経由となるため)。AtomS3 系の 16MHz に対してレジスタアクセスが 2 倍遅い。

**→ Atom Lite の SPI 速度は再検証する。結果次第で全機を AtomS3 Lite に揃えるか判断する。**
高レート側では AtomS3 系が有利。

### 5.4 同時性誤差

4 台巡回に 26ms かかるため、最初と最後の測距で時刻が 26ms ずれる。
ローバーが 1m/s で走行する場合 2.6cm のズレとなる。この速度域では無視してよいが、
高速走行させる場合は効いてくる。FC の慣性情報で補間することで吸収できる。

### 5.5 結論

- **10Hz は確実に達成できる**
- **30Hz は理論上ギリギリ届くが、現状の config のままでは不可能**。5.2 のパラメータ削減が前提
- 現実的には **10〜20Hz** を測位レートとし、FC 側の IMU/EKF で高レートに補間する構成を推奨
- UWB のレートを限界まで追うより、FC 側で慣性を積分し UWB で補正する方が滑らかで外れ値にも強い。
  UWB 測距が 1 周期落ちても位置推定を継続できる

まず現状のタグで `elapsedMs` の実測値を確認する。既にログに出力されているため、
1 測距の実時間が 6.5ms 前後に収まっているかを見れば、30Hz が射程かどうか判断できる。

## 6. IMU の扱い

Atom 内蔵 IMU は**使用しない**。ローバーにフライトコントローラを搭載しており、IMU はそちら側を使う。

参考: 現状のスケッチでは `cfg.internal_imu = false` としている。内部 I2C バスが UWB の RST / IRQ と
同じピンを使用するためであり、この設定は維持する。IMU をタグ側 Atom で使う必要がないため、
ピン競合の解決は不要となった。

タグ Atom と FC 間のインターフェース (UART / I2C / CAN 等) は別途検討する。

## 7. サーバー連携 (Wi-Fi)

### 7.1 データフロー

1. タグ起動 → Wi-Fi 接続
2. サーバーからアンカー座標表とバイアス補正値を取得 (HTTP/JSON を想定)
3. 取得したデータを NVS にキャッシュ
4. 以降の測位ループは Atom 内で完結。Wi-Fi が切断されても測位は継続
5. 走行中は測距結果と推定位置をサーバーへ送り続ける (デバッグ用のテレメトリ。UDP)

測位の計算自体はサーバーに依存しない。テレメトリが届かなくても走行には影響しない。

### 7.2 取得するデータ

```json
{
  "rev": 7,
  "pan_id": "0xDECA",
  "bias_mm": 0,
  "anchors": [
    { "id": "0x0100", "x": 0.000, "y": 0.000, "z": 1.800 },
    { "id": "0x0101", "x": 5.120, "y": 0.000, "z": 1.800 },
    { "id": "0x0102", "x": 5.080, "y": 4.310, "z": 1.800 },
    { "id": "0x0103", "x": 0.030, "y": 4.290, "z": 1.800 }
  ]
}
```

`id` は 2.2 の採番どおり UWB の `responderAddress` そのものである。アドレスを別フィールドに分けると
二重管理になるため持たせない。

サーバー側の詳細 (エンドポイント、データベース、テレメトリの受信) は
[server-design.md](server-design.md) にまとめる。本節は**タグから見た取得内容**のみを扱う。

### 7.3 NVS キャッシュの必要性

サーバーが落ちている、あるいは Wi-Fi が繋がらない状態でもローバーを動かせるようにするため、
取得済みの座標表は NVS に保存する。起動時はまずサーバーへ問い合わせ、失敗したらキャッシュにフォールバックする。
キャッシュも無い場合のみ測位不能として扱う。

### 7.4 Wi-Fi と UWB の同時動作 — 要検証

ESP32 の Wi-Fi タスクは比較的高い優先度で動作し、CPU を占有する時間帯がある。
一方 `respondDSRange()` / `requestDSRange()` の待機ループは `delay(1)` でポーリングしている
(`receiveFrame()` の実装と同様の構造)。

DS-TWR のフレーム送信タイミング自体は QM33120 チップ内部でハードウェア的にスケジュールされるため、
ホスト側の遅延がただちに測距精度を壊すわけではない。しかし、

- ホストのポーリングが Wi-Fi タスクに阻害され、受信完了の検出が遅れる
- 結果として `hostTimeoutMs` に達し、測距失敗としてカウントされる

という経路で**測位レートに影響する可能性がある**。

#### 方針: Wi-Fi は常時接続とする (決定)

デバッグのためにテレメトリを継続送信するため、**走行中も Wi-Fi は切らない**。
「座標表の取得後に `WiFi.mode(WIFI_OFF)` する」案は採らない。テレメトリが取れなくなり、
可視化による精度評価が成立しないためである。

そのうえで、レートへの影響は以下で抑え込む。詳細は [server-design.md](server-design.md) の 7.1 に書く。

- UWB 測距タスクを Core 1 に固定する (ESP32-S3 はデュアルコア。Wi-Fi は通常 Core 0)
- 送信は複数サイクルをまとめて UDP 1 発にし、巡回の先頭スロット直前に行う。測距と測距の間に割り込ませない
- Wi-Fi の再接続処理で測位ループをブロックしない

影響の大きさは実測で確認する。許容できない場合でも Wi-Fi を切るのではなく、
送信頻度を下げる方向で調整する。

## 参考: 確認済みのライブラリ挙動

`m5stack/M5Stamp-UWB` について、本検討にあたり確認した事項。

- `respondDSRange()` は `dst != responderAddress` のフレームを破棄する。ブロードキャスト受信は非対応
- `receiveFrame()` はアドレスフィルタを行わない。`src` / `dst` は `M5Stamp_UWBRxResult` として返る
- `M5Stamp_UWBFrameConfig.dst` のデフォルトは `0xFFFF` (ブロードキャスト)
- `requestDSRange()` / `respondDSRange()` は config を引数で受け取り、内部に役割状態を持たない。
  同一機体で initiator / responder を動的に切り替え可能
- `M5Stamp_UWBDSResponderResult.requester` には Poll 送信元アドレスが入る。
  Poll 未受信時は 0 のままで、非ゼロなら Poll/Response は成立して Final が失われたことを意味する
