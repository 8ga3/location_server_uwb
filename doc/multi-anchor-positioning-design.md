# マルチアンカー UWB 測位システム 設計メモ

M5Stamp-UWB (QM33120) を用いた DS-TWR 測距を、単一ペアからマルチアンカー測位へ拡張するための設計検討。
対象は Atom S3 / Atom S3 Lite / Atom Lite / Atom Matrix + M5Stamp-UWB。ライブラリは `m5stack/M5Stamp-UWB` を、
受信待ちを IRQ 割り込みにしたフォークで使う (末尾の「参考: M5Stamp-UWB のフォーク」)。

- 作成日: 2026-09-21
- 想定用途: ローバー型ラジコンの自己位置推定
- 現状: タグ 1 台 ⇔ アンカー 1 台の DS-TWR が動作済み

---

## 1. システム構成

```text
  [アンカー 0..N-1]        [タグ (ローバー搭載)]        [サーバー]
   M5Stamp-UWB             M5Stamp-UWB + Atom            アンカー座標表
   固定設置                 + フライトコントローラ          を保持
        |                          |                          |
        +----- UWB DS-TWR ---------+                          |
                                   +------- Wi-Fi ------------+
                                     起動時に座標表を取得
```

### 役割分担

| 要素 | 責務 |
| --- | --- |
| アンカー | UWB responder。固有 ID のみ保持。座標は持たない |
| タグ | UWB initiator。全アンカーを巡回測距 → 三辺測量で自己位置を算出 |
| サーバー | アンカー座標表とバイアス補正値を保持。タグへ配布 |
| FC (フライトコントローラ) | IMU による姿勢・慣性。Atom 内蔵 IMU は使用しない |

**測位計算はタグ側の Atom 内で実行する。** サーバーからは座標表を起動時に 1 度取得するだけで、
以降の測位ループはオフラインで完結する。Wi-Fi が切れても測位は継続できる。

## 2. アンカーアドレスの割り当て

### 2.1 制約

ライブラリの `respondDSRange()` は、受信フレームの `dst != responderAddress` の場合そのフレームを破棄する
(`.pio/libdeps/*/M5Stamp_UWB/src/M5Stamp_UWB.cpp` の該当箇所)。ブロードキャスト受信には対応していない。
したがって**アンカーごとにユニークな `responderAddress` が必須**である。

ただし、ここでいう「破棄」は受信を続けることではない。Poll を待っている間に自機宛てでないフレーム
(他アンカー宛ての Poll や、タグと他アンカーの間の Response / Final) を受けると、`respondDSRange()` は
そのフレームを捨てたうえで `RangeFrameMismatch` を返して終わる。複数アンカー構成では毎周期起きることなので、
呼び出し側はこれを失敗として扱わず、無通信 (NO POLL) と同じく次の `respondDSRange()` へ進む。
Final を待っている間の不一致は本当の異常なので、こちらは失敗として扱う。
両者は `txMarginUs` で見分ける。この値は Response の送信を予約した時点で入るため、未設定なら Poll 待ちでの
不一致である (実装は [main_anchor.cpp](../src/main_anchor.cpp) の `runResponder()`)。

また Poll フレームの宛先はタグ側が指定するため、**タグは各アンカーのアドレスを事前に知っている必要がある**。
このため「MAC アドレス下位 16bit を自動採番」のような方式は単体では成立しない (タグが知り得ない)。

### 2.2 採用方針 (実装済み)

16bit ショートアドレスを役割ごとの範囲に分け、**アドレスそのものを機体の ID として直接持たせる**。
別のオフセット値を介さないため、ログに出るアドレスと設定した ID が常に一致する。

```text
panId             = 0xDECA              (全機共通)
タグ              = 0x0001..0x00FF      (initiatorAddress)
アンカー          = 0x0100..0xFFFE      (responderAddress)
```

- タグは当面 1 台だが、下り TDoA (`downlink-tdoa-design.md`) では多数のタグが前提になるため 255 台分を予約しておく
- `0xFFFF` は 802.15.4 のブロードキャストアドレスなので、アンカーの上限は `0xFFFE`
- アドレスの上位側を見るだけでタグかアンカーかが判別でき、ID 空間が衝突しない

この設計により以下が成立する。

- タグはアンカー ID の一覧を順に叩くだけで全アンカーを巡回できる
- 巡回が実質的に TDMA として機能し、アンカー間の衝突が発生しない
- ライブラリの responder は受信フレームの `dst` と `panId` しか照合しない (`src` は見ない) ため、
  アンカー側はタグ ID を知らなくてよい。応答は常に Poll の送信元へ返される

タグが巡回するアンカー ID の一覧は、**起動時に測位サーバーから設置座標とあわせて取得する** (第 7 節 /
[server-design.md](server-design.md) 5.1)。取得した構成は NVS へキャッシュし、サーバーへ届かないときは
キャッシュで動作する。キャッシュも無い場合は巡回先が決まらないため測距を開始しない。

### 2.3 ID の設定方法 (実装済み)

ソースコードを直接書き換えて台数分ビルドする方式は避ける。以下を採用する。

#### 採用方式: NVS (Preferences) 保存 + 起動時のシリアル入力

当初検討した「ボタン長押しでインクリメント」方式は、画面のない Atom Lite / AtomS3 Lite では
現在値を提示できず (LED 1 個で 4 台以上の ID を表現できない)、採番 UI として成立しないため採用しない。
ボタンは**設定モードへ入るトリガのみ**に使う。

- 全機に同一ファームウェアをフラッシュする
- NVS namespace `uwb` / key `id` に 16bit で保存。再フラッシュしても保持される (`erase_flash` を実行しない限り)
- 起動時、ID が未設定 (または役割の範囲外) ならシリアル入力を待つ。**10 進数**で入力し、
  範囲外や数字以外は `ID_INPUT,result=ERR` を返して再要求する
- 入力待ちの表示: 画面のある AtomS3 は LCD に `SET ID` と入力中の値、画面のない Lite 系は
  **LED マゼンタ点灯**。マゼンタは通常動作の RED / YELLOW / GREEN と重ならないので一目で判別できる。
  Atom Matrix は 5x5 の LED をすべてマゼンタで点ける (通常動作中は状態の色で自機の ID を表示する)
- 電源投入またはリセット直後に本体ボタンが押されていれば、設定済みでも設定モードへ入る (現場での振り直し)
- 起動時ログに `DEVICE_ID,role=...,id=...,source=nvs|serial` を必ず出力する

シリアル入力を待つ間は UWB を初期化しない。ID が決まる前に電波を出さないためである。

実装はタグとアンカーで共通の [src/common/device_id.h](../src/common/device_id.h)。ボタンのピンは LED と同じ理由で
`getBoard()` ではなくビルドターゲットから決める (AtomS3 系 G41 / Atom Lite と Atom Matrix G39)。

## 3. 測位の原理と必要台数

### 3.1 測距と測位の区別

DS-TWR が返すのは距離スカラーのみである。座標を得るには、**既知のアンカー座標**と組み合わせた三辺測量が必要になる。
アンカー配置が事前に既知であることは、計算をどこで行うかに関わらず前提となる。

### 3.2 座標系

相対座標でよく、絶対座標や方位は不要。アンカー 0 を原点、アンカー 0→1 方向を X 軸に取るのが定石。
ただし**スケールは実寸**が必要なので、アンカー間距離は実測値を用いる。

### 3.3 必要台数 (測位側)

DS-TWR は真の距離を返すため、時刻バイアスの未知数が不要。

- **2D 測位 (高さ既知): 未知数 2 → 3 台で一意、4 台で冗長 1**
- 3D 測位: 未知数 3 → 4 台で一意、5 台で冗長 1

重要なのは「設置台数」ではなく「**その瞬間に見えている台数**」である。4 台設置でも遮蔽により 3 台しか届かなければ
冗長ゼロ、2 台なら測位不能となる。ローバーの場合、車体自身や障害物による遮蔽が発生しうる。

### 3.4 配置 (GDOP)

- アンカーを一直線または一直線に近い形に配置すると、解が極端に不安定になる
- 測距誤差 10cm が位置誤差 1m 級に増幅されうる
- 4 台なら**正方形に近い配置**とし、タグ (ローバー) は 4 台が作る四角形の**内側**を走行させる
- 四角形の外に出ると精度が急落する

### 3.5 初期方針

**2D 測位・アンカー 4 台・座標は手測り**から開始する。

- 高さは全アンカー同一とし、2D 問題として解く
- ローバーは地上を走るため高さ方向の変動が小さく、2D で十分
- 自動推定 (self-survey) は後述するが、初期段階では手測りで確実に動かす

### 3.6 タグ側の 2D 測位 (実装済み)

タグは巡回の 1 周期を終えるたびに、その周期の測距から自己位置を求める
([trilateration.h](../src/common/trilateration.h)、[main_tag.cpp](../src/main_tag.cpp) の `solvePosition()`)。

#### 解き方

- 未知数は水平位置 x, y の 2 つにし、タグの高さはビルドフラグ `UWB_TAG_Z_MM` の固定値 (既定 0) で与える。
  アンカーとの高さの差を含めた斜距離の式に対して最小二乗を解く。測距値を水平距離とみなすと、
  アンカーを高く付けたときに位置が外側へずれるためである
- 測距値にはサーバーの構成の `bias_mm` を足してから使う
- 初期値は線形化した最小二乗で作る。各アンカーの式から先頭のアンカーの式を引いて 2 乗の項を消し、
  x, y の 1 次式にしたものである。そこから Gauss-Newton 法で残差の 2 乗和を最小にする
  (最大 10 回、更新量 0.1 mm 未満で収束とみなす)
- 計算は float で行う。ESP32 / ESP32-S3 の FPU は単精度だけで、double はソフトウェアの演算になる。
  桁落ちを抑えるため、アンカーの重心を原点にずらしてから解く

#### 解けない周期の扱い

次の周期は `fix_flags` の bit0 を 0 にしてテレメトリへ送り、サーバーは最小二乗の座標を NULL で保存する。
フィルタ (3.7) はこれらの周期でも残った測距で更新するか、予測だけでつなぐ。

- 解に渡せる測距が 3 本未満 (`TOO_FEW`)。応答したアンカーの数ではなく、下に書く負の値を除いたあとの本数で数える
- 配置が悪く、2 方向を区別できない (`GEOMETRY`)。正規方程式の 2x2 行列の条件数がおよそ 4000 を
  超えたら解けないものとする
- 計算の途中で NaN / 無限大が出た (`NON_FINITE`)

反復の上限までに収束しなかった場合も、有限の値が出ていれば解として送る。発散の様子を残差と一緒に
見るためである ([server-design.md](server-design.md) の 6.2)。

ライブラリが成功として返した測距に、まれに `-14136` mm や `-36585` mm のような負の値が混ざる。
30Hz で 1 分に 2 回 (どちらも 0x0100) 出た一方、次の 2 分では 1 回も出なかった。そのまま解に入れると
初期値が遠くへ飛び、周期ごと `GEOMETRY` で落ちる。そこで -500 mm を下回る測距は解に渡さず、残りの
本数で解く。テレメトリには生の値をそのまま送る。捕まえた 2 周期から 0x0100 を外して解くと、
実測の位置との差は 1.2〜1.7cm だった。原因の調査は、この節の末尾の「負の測距値の調査」に書く。

シリアルには 2 秒ごとに `POS,...` の 1 行 (直近の解と、解けなかった周期の理由ごとの件数、計算時間の最大値) を
出す。`GEOMETRY` と `NON_FINITE` の周期は `POS_FAIL,...` で測距値を、解から外した測距は `POS_REJECT,...` を
その場で出す。どちらも種類ごとに 1 秒に 1 行までに抑え、出さなかった分は `POS` 行の件数で追う。置き方が悪いと
毎周期起きうるため、30Hz で毎周期書くとシリアルの送信が測距ループを止める。`TOO_FEW` は遮蔽で続けて起きうるので
件数だけを数える。

#### 静的精度の実測 (2026-09-29)

AtomS3R のタグとアンカー 4 台を同じ高さに置き、タグから各アンカーまでの距離を巻尺で測って比べた。
巻尺の 4 本から最小二乗で求めた位置を真値とした。4 本の食い違いは最大 13 mm である。

| 設置 | 配置 | 平均位置の誤差 | 位置のばらつき (標準偏差) | 残差 RMS |
| --- | --- | --- | --- | --- |
| 鉄筋コンクリートの床に直置き | 1.0 m 四方 | 45 mm | x 13 mm / y 22 mm | 20〜50 mm |
| 高さ 400 mm のローテーブルの上 | 0.9 m × 0.6 m | 28〜36 mm (最大 67 mm) | 11〜14 mm | 中央値 38 mm |

- 床置きでは 0x0102 だけが巻尺より約 100 mm 短く出た。0x0102 を動かすと差は縮み、アンテナの向きでも
  大きく変わった。テーブルの上へ移すと 0x0102 だけの偏りは消えたので、個体差ではなく設置環境
  (床の反射と、直接波の通り道 (第 1 フレネルゾーン) に床がかかること) によるものと判断した。
  ch9 (約 8GHz) では、第 1 フレネルゾーンの半径は距離 1 m で約 10 cm、5 m で約 21 cm になる
- 床置きの最初の試験では、0x0101 の近くに人の足があり、0x0101 の測距が 40 cm の幅でばらついた
- テーブルの上では 4 台とも巻尺より 18〜70 mm 短かった (平均 44 mm)。台数ぶんの共通のずれとしては
  説明しきれず、`bias_mm` 1 つでは補正できない
- Gauss-Newton の反復は、テーブルの上で 2〜4 回、床置きで 6〜7 回 (まれに 10 回で打ち切り) だった。
  残差が大きく、近いアンカー (約 0.3 m) があると収束が遅くなる。打ち切った解も妥当な値だった

計算時間は 1 周期あたり最大 116 µs で、30Hz の 1 スロット (8 ms) に対して十分に小さい (7.4)。

#### 負の測距値の調査 (2026-09-29)

距離はアンカー側の `respondDSRange()` が 4 つの区間から計算し、Result フレームでタグへ返す。

- `ra`: タグの Poll 送信 → Response 受信
- `da`: タグの Response 受信 → Final 送信
- `rb`: アンカーの Response 送信 → Final 受信
- `db`: アンカーの Poll 受信 → Response 送信

飛行時間は `(ra * rb - da * db) / (ra + rb + da + db)` で求める。`da` と `db` は、受信時刻から一定の遅延で
送信を予約するので、受信時刻がずれても変わらない。そのため、ある受信時刻が δ だけ早く出ると次のようになる。

- アンカーの Poll 受信が早い: 予約した Response も δ 早く出るので `ra` だけが δ 縮む
- アンカーの Final 受信が早い: `rb` だけが δ 縮む
- タグの Response 受信が早い: 予約した Final も δ 早く出るので、`ra` と `rb` が両方 δ 縮む。
  アンカーの Poll 受信と Final 受信が同じ交信で両方ずれた場合と区別できない

`ra` が δ 縮むと、飛行時間はおよそ `δ * rb / (ra + rb + da + db)`、つまり δ の約 0.27 倍だけ短くなる。

調査のため、フォークで 4 区間を結果に入れ、0x0100 のアンカーで -500 mm を下回った測距の 4 区間を記録した。
30Hz で 10 分ずつ測った結果は次のとおり。

| 条件 | 0x0100 の外れ値 |
| --- | --- |
| 0x0100 が落下したあと置き直し、PC と USB で接続 | 105 件 |
| 同じ置き方で、給電を PC から充電器へ切り替え | 81 件 |
| 0x0100 と 0x0102 の置き場所を入れ替え | 0 件 |

- 外れ値はすべて 0x0100 で、受信時刻はいつも早い側にずれていた。ずれの幅は **約 56.3 ns (約 3600 DTU)** と
  **約 248 ns (約 15900 DTU)** の 2 つに固まり、それぞれ ±1 ns 程度に揃っていた。通常の測距での区間の
  ばらつきは 7〜12 ns である
- 105 件の内訳は、`ra` だけが縮んだもの (アンカーの Poll 受信) 38 件、`rb` だけが縮んだもの (アンカーの
  Final 受信) 30 件、両方が縮んだもの 37 件だった。両方の件がアンカー側の 2 回の受信なのか、タグの
  Response 受信なのかは、4 区間からは決められない
- 決まった幅だけ早く出ることから、受信側のチップが受信波形 (CIR) の立ち上がりより手前にある偽のピークを
  first path と判定していると考えている。CIR の診断値 (first path とピークの位置) は読んでいないので、
  確かめてはいない
- 落下する前の 0x0100 では 1 分に 0〜2 回だった。置き場所を入れ替えると、0x0100 を別の位置に移しても、
  0x0102 を 0x0100 のもとの位置に置いても出なくなった。機体の故障や場所そのものではなく、置き直したときの
  向きや傾き、ケーブルの取り回しなどが効いていたと判断した。どれが効いていたかは切り分けていない
- 0x0100 を PC と USB で繋いでいる間は、0x0101 の `RX_ERROR` が約 3% (10 分で 559 件) に増えた。
  USB を外すと 10 分で 3〜6 件に戻った

外れ値はすべて -3.2 m 以下で、タグ側の -500 mm の除外で確実に弾けている。アンカー側で弾く処理
(クロックのずれを補正したうえで、片側ずつの往復の食い違いを見る) は入れていない。調査用の変更も
取り込んでいない。再び増えたときは、まず外れ値を出すアンカーの置き方を見直す。

### 3.7 タグ側のカルマンフィルタ (実装済み)

タグは 3.6 の最小二乗とは別に、拡張カルマンフィルタ (EKF) で位置を推定する
([position_filter.h](../src/common/position_filter.h)、[main_tag.cpp](../src/main_tag.cpp) の `filterPosition()`)。
走行中は静止時より位置の誤差が大きくなる ([server-design.md](server-design.md) のフェーズ C の走行試験)。
FC 側の IMU 統合 (フェーズ 7) の前に、UWB の測距だけで位置を滑らかにし、外れ値と欠測に強くするためである。

#### 方式: 測距値を直接の観測にする EKF (決定)

3.6 の最小二乗の解を観測にする線形のカルマンフィルタではなく、測距値 1 本ずつを観測にする EKF を採った。

- 最小二乗が解けない周期 (`TOO_FEW`、`GEOMETRY`) でも、残った測距で更新できる。遮蔽で 1〜2 台が落ちる周期は
  よく起きるので、そのたびに予測だけに頼りたくない
- 外れた測距を 1 本ずつ棄却できる。最小二乗の解を観測にすると、外れた測距は解全体のずれとしてしか現れず、
  どの測距が悪いかが分からない
- 巡回のスロットごとに測距の時刻がずれる (10Hz・4 台で 25 ms ずつ。5.4)。測距ごとにその時刻まで予測を
  進めてから取り込むので、1 周期の測距を同時とみなすことによるずれがフィルタ後の位置には入らない
- 3D (フェーズ 6) へは、状態に z と鉛直の速度を足し、観測行列に z の成分を足せば広げられる
- 観測は 1 本ずつのスカラーなので、更新に逆行列が要らない。状態は 4 つで、計算量は最小二乗と同程度に収まる

フィルタはタグで動かす。測位計算をタグで完結させる役割分担 (1 章) を崩さず、Wi-Fi が切れてもフィルタ後の
位置を出し続けられるようにするためである。

#### モデルとパラメータ

状態は水平位置と速度 (x, y, vx, vy) で、運動モデルは等速度とする。加速度を白色雑音とみなし、
プロセスノイズに入れる。観測は 1 本の測距 (斜距離) で、タグの高さは最小二乗と同じ固定値
(`UWB_TAG_Z_MM`) で与える。取り込む測距は最小二乗に渡すものと同じで、`bias_mm` を足し、-500 mm を
下回る値を除いたものである (3.6)。

| 項目 | 値 | 理由 |
| --- | --- | --- |
| プロセスノイズ (加速度のパワースペクトル密度) | 1 m²/s³ | ローバーの加減速 (1 m/s² 程度) を見込んだ |
| 観測ノイズ (測距 1 本の標準偏差) | 80 mm | 静止時のばらつき 10〜20 mm に、補正しきれないアンカーごとのずれを含めた。ずれは 3.6 では 18〜70 mm だったが、置き方によっては 280 mm 近くになる (後述の 2026-10-05 の試験) |
| 棄却のしきい値 | 正規化したイノベーションの 2 乗 > 16 | 標準偏差の 4 倍。3.6 の負の外れ値 (-3.2 m 以下) は確実に弾ける |
| 初期化に使う最小二乗の解の残差 RMS の上限 | 150 mm | 静止時の残差は 20〜50 mm。これより大きい解は外れた測距を含む疑いがある |
| 初期化したときの標準偏差 | 位置 0.1 m、速度 1 m/s | 速度は分からないので 0 とし、走行中に初期化しても追い付ける幅を持たせた |
| 予測だけでつなぐ上限 | 1 秒、位置の標準偏差 0.5 m | 次の節 |

値は [position_filter.h](../src/common/position_filter.h) の定数で、起動時に `POS_KF_CONFIG,...` として
シリアルへ出す。いずれもシミュレーション (後述) で決めた初期値で、実機のデータで調整する。
プロセスノイズだけは、実機で値を比べるためにビルドフラグ `-D UWB_KF_ACCEL_PSD=<値>` で変えられるようにした。

- 初期値は、フィルタが無効なときに最小二乗が解け、その残差 RMS が 150 mm 以下だった周期の解から作る。その周期の測距は最小二乗の解に
  使ったものと同じなので、フィルタへは取り込まない (同じ観測を 2 回使うことになる)
- 1 周期の測距は巡回の順 (時刻順) に取り込む。各測距の時刻は、`requestDSRange()` を呼ぶ直前の `millis()` とする。
  スロットの基準時刻ではないのは、先頭スロットでは基準時刻を取った後にテレメトリの送信が入るためである
- 出力する位置は、周期の最後のスロットの時刻まで予測を進めたものである。測距が 1 本も無い周期も同じ時刻まで
  予測を進めるので、毎周期同じ時刻の位置が出る

#### 予測だけでつなぐ範囲

最後に測距を取り込んでから 1 秒を超えるか、位置の標準偏差 sqrt(Pxx + Pyy) が 0.5 m を超えたら、
フィルタ後の位置を無効にする。上限がないと、実測のない位置を際限なく有効として出し続けてしまう。
1 秒は 10Hz で 10 周期、30Hz で 30 周期にあたる。

- 無効にした後は、次に最小二乗が解けて、その残差 RMS が 150 mm 以下だった周期で初期化し直す。無効にしたのと
  同じ周期でこの条件を満たしていれば、その周期のうちに初期化する。残差が 150 mm を超える解は外れた測距を含む
  疑いがあるので初期値に使わず、その間はフィルタ後の位置を無効のままにする
- 測距をすべて棄却し続けた場合も、取り込めない時間が延びて無効になる。そのときはフィルタの状態のほうが
  外れていたとみなし、最小二乗の解で初期化し直す
- 速度の不確かさがあるため、測距がまったく無いと位置の標準偏差は速く広がる。後述のシミュレーションでは、
  1 秒の上限より先に 0.5 秒 (10Hz で 5 周期) で標準偏差の上限に達した
- 測距が 1〜2 本だけ残る周期は、その本数で更新を続ける。1 本では測距の方向にしか効かないので、
  それと直交する方向の不確かさは広がり、続けば標準偏差の上限で無効になる

#### テレメトリとシリアル

テレメトリのサイクルレコードには、最小二乗の解とは別にフィルタ後の位置と標準偏差、取り込んだ測距と
棄却した測距の本数を入れる。`fix_flags` の bit2 がフィルタ後の位置の有効、bit3 が観測で更新したこと
(0 なら予測だけ)、bit4 が最小二乗の解で初期化したことを表す ([server-design.md](server-design.md) の 6.2)。

シリアルには 2 秒ごとに `POS_KF,...` の 1 行 (直近の周期の状態と位置・速度・標準偏差、観測で更新した周期・
予測だけの周期・無効だった周期・初期化・棄却した測距の件数、無効にした理由ごとの件数、計算時間の最大値) を出す。
無効にした周期は `POS_KF_RESET,...` をその場で出し、1 秒に 1 行までに抑える。`POS` 行の形は変えない。
LCD の x, y にはフィルタ後の位置を出し、観測で更新した周期は緑、予測だけの周期は黄にする。

#### ホストでのシミュレーション (2026-10-01、2026-10-05 に観測ノイズ 80 mm で再計算)

実機の評価の前に、ホストの C++ コンパイラでフィルタと最小二乗を同じ測距に掛けて比べた
([tools/position_filter_sim.cpp](../tools/position_filter_sim.cpp))。最初は観測ノイズ 50 mm で計算し、
2026-10-05 に 80 mm へ変えたとき (後述) に計算し直した。表と箇条書きは 80 mm の値である。条件は次のとおり。

- アンカー 4 台を 5 m × 4 m の四隅、高さ 1.8 m に置き、タグの高さは 0.2 m
- 10Hz、1 スロット 25 ms。測距には標準偏差 20 mm の雑音と、アンカーごとに -18〜-70 mm の一定のずれを足す
- 1% の測距に +0.6 m の外れ値 (反射波を拾った場合を想定) を足す
- 60 秒のうち、2 秒は全アンカーを遮蔽し、別の 4 秒は 2 台を遮蔽する (`TOO_FEW` が 40 周期続く)
- 位置の誤差は、どちらも周期の最後のスロットの時刻の真値に対して測る。最小二乗の解は 1 周期の測距を
  まとめて解くので、走行中はこの時刻に対して遅れたぶんも誤差に含まれる
- 表の誤差は、最小二乗の解とフィルタ後の位置がどちらも有効な周期 (539〜540 周期) だけで比べる。フィルタだけが
  有効な周期 (2 台を遮蔽した間や予測だけの周期) を片方にだけ入れると、同じ周期の比較にならないためである
  ([server-design.md](server-design.md) の 8.4 と同じ考え方)。それらの周期は表の下の箇条書きで別に扱う

| 走行 | 外れ値 | 最小二乗の RMS 誤差 | フィルタの RMS 誤差 (50 mm のとき) | 棄却した測距 |
| --- | --- | --- | --- | --- |
| 静止 | なし | 28 mm | 20 mm (22 mm) | 0 本 |
| 静止 | 1% | 78 mm | 21 mm (23 mm) | 24 本 (外れ値 25 本) |
| 半径 1.5 m の円を 1 m/s | なし | 57 mm | 36 mm (39 mm) | 0 本 |
| 半径 1.5 m の円を 1 m/s | 1% | 89 mm | 36 mm (39 mm) | 24 本 (外れ値 25 本) |
| 半径 1.5 m の円を 2 m/s | 1% | 114 mm | 40 mm (34 mm) | 24 本 (外れ値 25 本) |

乱数の種はどれも 1 で、`position_filter_sim <速度> <外れ値の割合> 1` の結果である。棄却した測距の本数は
50 mm のときと同じだった。

- 静止時はアンカーごとのずれが誤差の大半を占め、フィルタでは減らない。ずれは測距そのものの補正
  (9 章の未決事項) で詰める
- 棄却しなかった外れ値 1 本は最初の周期に入ったもので、フィルタはまだ無効だった。その周期の最小二乗の解は
  残差が 215 mm で上限を超えたので初期化に使わず、次の周期で初期化した。外れ値を含む周期の残差は 133〜223 mm で、
  初期化の残差の上限 (150 mm) ですべてを弾けるわけではない
- 2 台を遮蔽した 4 秒間は、最小二乗は 1 周期も解けず、フィルタは残った 2 本で更新を続けた
  (1 m/s で RMS 誤差 66 mm、最大 118 mm。2 m/s では RMS 誤差 92 mm で、50 mm のときの 69 mm より悪い)
- 全アンカーを遮蔽した 2 秒間は、5 周期 (0.5 秒) を予測でつないだあと標準偏差の上限で無効にし、測距が戻った
  周期に最小二乗の解で初期化し直した。予測だけの間は誤差が速く広がり、2 m/s では無効にする直前で 630 mm
  (そのときの標準偏差は 477 mm) になった。フィルタの位置が有効な周期全体で見ると、最大誤差はどの条件でも
  この予測の区間で出ている

#### 実機での静止試験 (2026-10-04)

AtomS3R のタグをアンカー 4 台 (0.9 m × 0.6 m) の中に置いたまま、10Hz で動かした。指標は
[server-design.md](server-design.md) の 8.4 の定義で、サーバーの `tools/filter_compare.py` で求めた。
フィルタの計算時間は 1 周期あたり 82〜114 µs だった。

| プロセスノイズ | 記録 | 散らばり RMS の比 | 跳び RMS (最小二乗 → フィルタ) | 50 mm を超える跳び |
| --- | --- | --- | --- | --- |
| 1.0 m²/s³ (既定) | 740 秒 | 0.80 (38.9 → 31.2 mm) | 22.2 → 18.6 mm (0.83) | 90 → 24 回 |
| 0.1 m²/s³ | 100 秒 | 0.80 (16.8 → 13.4 mm) | 22.7 → 12.5 mm (0.55) | 14 → 1 回 |

比はフィルタの値を最小二乗の値で割ったものである。この 2 つの記録は、0x0102 と 0x0103 の y を実際より
0.1 m 大きく (0.7 m と) 登録したまま解いたもので、真値とも比べていない。周期ごとの揺れの比較には使えるが、
位置そのものの精度は次の試験で見る。

- 外れ値で最小二乗の解が跳んだ周期は、フィルタがよく抑えた。別の記録 (プロセスノイズ 1.0) で最小二乗が
  300 mm 以上跳んだ 5 周期では、フィルタの動きは 7〜114 mm だった (最小二乗は 304〜557 mm)。
  そのうち 3 周期では、フィルタが測距を 1 本棄却していた
- 静止時の散らばりは 2 割しか減らない。散らばりの多くは周期ごとの雑音ではなく、ゆっくり動く成分である
- プロセスノイズ 0.1 の記録は 100 秒しかない。シミュレーション (両方が有効な周期で比較) では、0.1 にすると
  1 m/s までは少し良くなる (1 m/s で 39 → 33 mm) が、2 m/s の旋回では 34 → 79 mm に悪くなり、0.03 では
  発散した。走行試験の前に値を決め直す

真値の分かる位置にタグを置いた試験 (プロセスノイズ 1.0) では、テレメトリの測距を正しい座標で解き直して
真値と比べた。タグ自身は誤った座標のまま解いていたためである。

| 記録 | 真値 (x, y) | 最小二乗の RMS 誤差 | フィルタの RMS 誤差 | 棄却した測距 |
| --- | --- | --- | --- | --- |
| 11 分 | (0.40, 0.36) m | 38 mm | 30 mm | 6 本 |
| 15 分 | (0.40, 0.40) m | 133 mm | 100 mm | 258 本 |

- どちらもフィルタのほうが真値に近い。アンカーごとの測距の偏りは揃っておらず、1 回目の記録では
  0x0100 / 0x0101 / 0x0102 / 0x0103 の順に約 −125 / −40 / −100 / −45 mm (真値の距離より短い) だった。
  0x0100 は数分のうちに −76〜−159 mm の間で変わった
- 2 回目の記録では、人の近くに置いた 0x0100 の測距が真値より 70〜350 mm 長くなった。人がわずかに動くだけで
  変わり、体が直接波を遮っていると考えている。0x0100 が大きく外れた 2 分間は、最小二乗の RMS 誤差 227 mm に
  対してフィルタは 93 mm で、測距を 234 本棄却していた
- 偏りの補正と、人の近くのアンカーの扱いは [issue #10](https://github.com/8ga3/m5atom_uwb_ds_twr/issues/10) で検討する

この節の試験は、どれも観測ノイズ 50 mm のファームで行った。

#### 広い配置での試験と観測ノイズの見直し (2026-10-05)

アンカー 4 台を 2.37 m × 1.75 m の四隅、高さ 0.25 m に置いた (サーバーの `rooms/room-1.json`)。AtomS3R の
タグを使い、10Hz、プロセスノイズ 1.0、観測ノイズ 50 mm で記録した。

まず、タグを (1.50, 0.60) m 付近、高さ 0.275 m に置いて静止させた。メジャーで測ったアンカーまでの距離から
解いた位置 (1.507, 0.636) m を真値とする (4 本の残差は ±24 mm 以内)。同じ場所でタグを 180° 回した記録も取った。

| 記録 | タグの向き | 長さ | 最小二乗の RMS 誤差 | フィルタの RMS 誤差 | 棄却した測距 |
| --- | --- | --- | --- | --- | --- |
| #2752 | 元の向き | 12 分 | 163 mm | 175 mm | 48 本 |
| #2753 | 180° 回転 | 10 分 | 144 mm | 262 mm | 5832 本 (96% の周期) |

測距の中央値とメジャーの距離の差は次のとおりで、記録の間はほぼ一定だった (1 分ごとの中央値の変化は 10〜20 mm)。

| アンカー | #2752 | #2753 |
| --- | --- | --- |
| 0x0100 (0, 0) | −260 mm | −169 mm |
| 0x0101 (2.37, 0) | −20 mm | −62 mm |
| 0x0102 (2.37, 1.75) | +35 mm | +61 mm |
| 0x0103 (0, 1.75) | −226 mm | −283 mm |

- x = 0 側の 2 台だけが 170〜280 mm 短い。タグを回しても偏りは同じ 2 台に残ったので、タグのアンテナの向きが
  主な原因ではない。2 台は機種が違う (AtomS3 と Atom Matrix)。原因は
  [issue #10](https://github.com/8ga3/m5atom_uwb_ds_twr/issues/10) で調べる
- #2753 では、フィルタが 96% の周期で測距を 1 本 (まれに 2 本) 棄却し、残りの 3 本に合う位置で固まった。
  偏り (0x0103 の −283 mm) が棄却の幅 (観測ノイズ 50 mm で約 ±260 mm) を超えると、そのアンカーを棄却し、
  フィルタが残りの測距に寄るので、棄却したアンカーとの差はさらに広がる。測距は途切れないのでフィルタは
  有効なままで、初期化し直す機会もない
  ([issue #12](https://github.com/8ga3/m5atom_uwb_ds_twr/issues/12))

続いて、タグをローバーに載せ (高さ 0.21 m)、アンカーの内側を約 6 分間ランダムに走らせた (#2754)。速さは
フィルタの位置の 1 秒間の移動量で中央値 0.5 m/s、最大 1.3 m/s だった。真値は無いので、周期ごとの揺れで比べた。

- 跳び RMS は最小二乗 127 mm に対してフィルタ 98 mm、跳びの最大は 649 mm に対して 315 mm だった。
  最小二乗が 200 mm を超えて跳んだ周期の多くで、フィルタの動きは 100 mm 前後だった
- フィルタと最小二乗の位置の差は、時刻をずらさないときが最小で、フィルタの遅れは見られなかった
- 走り終えて止めた区間の一つでは、#2753 と同じくフィルタが 95% の周期で棄却し、最小二乗から 150 mm 離れた
  位置で固まった

記録した測距をファームと同じコードで解き直し、改善案を比べた。改善前のコードで解き直した位置は、テレメトリの
フィルタの位置と 1 mm 未満で一致した。外れ値に対する強さは前述のシミュレーションで見た。

| 案 | #2753 の RMS 誤差 | #2753 で棄却した周期 | #2754 の止めた区間の最小二乗との差 | シミュレーション 2 m/s |
| --- | --- | --- | --- | --- |
| 観測ノイズ 50 mm (変更前) | 262 mm | 96% | 151 mm | 34 mm |
| 観測ノイズ 80 mm | 175 mm | 0% | 48 mm | 40 mm |
| 観測ノイズ 100 mm | 171 mm | 0% | 43 mm | 63 mm (外れ値 25 本中 10 本を取り込む) |
| Huber 型の重み付け (c = 3) | 194 mm | 0% | 53 mm | 44 mm (外れ値をすべて取り込む) |
| 棄却の幅に 0.4 m の下限 | 183 mm | 0.1% | 61 mm | 34 mm |
| 同じアンカーを 10 周期続けて棄却したら弱い重みで取り込む | 222 mm | 61% | 109 mm | 34 mm |

- 棄却の幅に下限を付けると、走行中に外れた測距を強い重みで取り込み、#2754 の走行区間で跳びの最大が
  0.6 m (下限 0.4 m) 〜 4.1 m (下限 0.3 m) になった
- 続けて棄却したときだけ扱いを変える案 (弱い重みで取り込む、初期化し直す) は、棄却と取り込みを繰り返して
  位置が揺れ続けた
- 観測ノイズを 80 mm にした。実機の 3 つの記録すべてで棄却し続ける現象が消え、シミュレーションで棄却する
  外れ値の本数は 50 mm のときと同じだった。静止時の棄却の幅は約 ±370 mm で、今回の偏りに対する余裕は
  約 90 mm である。人の体で測距が 350 mm 長くなるような乱れ (前節) は引き続き棄却する
- どの案でも #2753 は最小二乗 (144 mm) より少し悪い。アンカーごとの一定の偏りが残る限り、フィルタで真値に
  近づけることはできない。数百 mm の精度で足りる用途 (GNSS の無い場所でのおおよその位置) では、偏りの補正
  より先に、偏りがあっても破綻しないことを優先した

## 4. アンカー座標の自動推定 (self-survey) — 将来の拡張

手測りが動作した後の拡張として検討する。

### 4.1 ライブラリ側の実現可能性 (確認済み)

- `receiveFrame()` はアドレスフィルタを一切行わない。`src` / `dst` は結果として返るのみ。
  → 任意の制御メッセージの受信に使える
- `M5Stamp_UWBFrameConfig.dst` のデフォルトは `0xFFFF` (ブロードキャスト)
- `requestDSRange()` / `respondDSRange()` は毎回 config を引数で受け取り、内部に役割状態を持たない。
  → **同一機体で呼び分けるだけで initiator / responder を切り替えられる**

### 4.2 手順

#### フェーズ 0: サーベイモード起動

通常の responder ループを抜けて survey モードへ入る。トリガはボタン長押しまたはシリアルコマンド。

#### フェーズ 1: 相互測距

1. マスター 1 台 (アンカー 0 で固定してよい) がブロードキャストで `ROUND=i` を告知する
2. `anchorId == i` の機体が initiator となり、`responderAddress` を書き換えながら j = 0..N-1 (j≠i) を順に `requestDSRange()`
3. **それ以外の全機体は `respondDSRange()` を回しっぱなしにする。** 自分宛でないフレームは dst 不一致で破棄されるため、調停は不要。
   このとき返る `RangeFrameMismatch` は失敗として扱わない (2.1 節)
4. ラウンド完了後 `DONE` をブロードキャストし、マスターが `ROUND=i+1` へ進める

両方向 (i→j と j→i) を測定して平均すると、アンテナ遅延の非対称性が均される。
各ペア 20 回程度測定し**中央値**を採ってマルチパス外れ値を除去する。

#### フェーズ 2: 距離行列の集約

各 initiator が `D,i=0,j=3,mm=4213` 形式でシリアル出力する。マスター 1 台を PC に接続し、
ブロードキャストで報告を集めて一括出力する方式でもよい。

#### フェーズ 3: 座標計算 (PC 上で実行。ESP32 で行う必要はない)

1 回限りの作業なので Python が適している。

古典的 MDS で初期解を得る。

1. 対称化: `d_ij = (d_ij + d_ji) / 2` として N×N 距離行列 D を構成
2. 二重中心化: `J = I - (1/N) * ones((N,N))` として `B = -0.5 * J @ (D**2) @ J`
3. B を固有分解し、固有値の大きい順に k 個 (2D なら k=2) を取る
4. `X = V_k @ sqrt(diag(lambda_k))` が初期座標 (N×k)

次に非線形最小二乗で精密化する (`scipy.optimize.least_squares`)。

残差を `r_ij = ||x_i - x_j|| + b - d_ij` と定義して最小化する。
`b` はアンテナ遅延由来の共通オフセットであり、**未知数に加えて同時推定する**のが要点。
ここで得た `b` はタグ測位時の距離にも同様に効くため、補正値として保存しサーバー側で配布する。

#### フェーズ 4: ゲージ固定

MDS の解は並進・回転・鏡映が自由なので固定する (2D の場合)。

1. 平行移動: アンカー 0 を原点へ移す
2. 回転: アンカー 1 が +X 軸上に来るよう全体を回転
3. 鏡映: アンカー 2 の y が正になるよう、必要なら y の符号を反転

これで数値的には一意に定まる。ただし**実世界のどちら向きかは決まらない**。
「アンカー 2 は実際に 0→1 方向から見て左か右か」の 1bit だけは人が目視で判断する必要がある。ここは自動化できない。

#### フェーズ 5: 検証

- **残差 RMS**: 数 cm〜10cm 程度なら妥当。それ以上なら遮蔽や NLOS を疑う
- **スケール照合**: 1〜2 辺をメジャーで実測して比較する。系統的にずれていればバイアス `b` の推定が効いていない
- **固有値チェック**: 2D なら λ3 が λ1, λ2 に対して十分小さいこと。大きければ配置が平面でない

### 4.3 self-survey に必要な台数

2D で自由度を数える。

- 未知数: N 点 × 2 = `2N`、ゲージ固定で −3 (並進 2 + 回転 1)、バイアス b を +1 → **2N − 2**
- 観測数: ペア数 = **N(N−1)/2** (両方向は平均するため 1 ペア 1 拘束)

| N | 観測数 | 有効未知数 | 冗長度 |
| --- | --- | --- | --- |
| 3 | 3 | 4 | 解けない (b を諦めれば辛うじて一意) |
| 4 | 6 | 6 | **0 — 一意だが自己検証不能** |
| 5 | 10 | 8 | 2 |
| 6 | 15 | 10 | 5 |

**N=4 では残差が常に 0 になる。** 測距が 1 本ずれていても、それを吸収する形に座標が動くだけなので、
残差からは異常を検出できない。

注意: 各ペアを 20 回測定しても幾何的な冗長性は増えない。繰り返しはノイズ平均化にしか効かず、
形の拘束数は**ペア数のみ**で決まる。

結論として、**self-survey を検証込みで運用するには 5 台以上が必要**。
4 台で self-survey を試すこと自体は構わないが、必ず手測り値と突き合わせること。

### 4.4 高さ (Z) の扱い

**アンカーを全て同じ高さに設置すると、相互測距だけでは Z が決まらない** (同一平面の退化)。
「2D は自動推定、高さは手測り」を推奨する。3D を自動化する場合は、数台を意図的に異なる高さに設置する必要がある。

### 4.5 運用上の注意

- survey 中の見通しは必須。遮蔽されたペアは系統的に長い距離として出る。残差の大きいペアは除外して再計算する
- アンカーを移設するたびに survey を再実行する。ボタン起動にしておくと現場で回せる

## 5. 測位レートの検討

目標: **最低 10Hz、可能なら 30Hz**。

### 5.1 時間予算

`M5Stamp_UWBDSRangeConfig` ([uwb_link.cpp](../src/common/uwb_link.cpp) の `initUwb()`) で DS-TWR 1 回を積算する。
uus (UWB microsecond) ≈ 1.0256µs。当初の設定値で見積もった。

| 項目 | 設定値 | 実時間 |
| --- | --- | --- |
| `responseTxDelayUus` | 3000 uus | 3.08ms |
| `finalTxDelayUus` | 1800 uus | 1.85ms |
| `resultRxAfterFinalTxDelayUus` | 500 uus | 0.51ms |
| フレーム空中時間 (4 本) | — | 約 1ms |
| **合計 (支配項)** | | **約 6.5ms / 測距** |

4 アンカー巡回で 26ms ≈ 38Hz。数値上は 30Hz に乗るが余裕はない。

実測では、タグ側の `elapsedMs` (Poll の送信から距離通知の受信まで) は 6〜7ms で見積もりどおりだった。
`finalTxDelayUus` を 1200 に下げると 5〜6ms、さらにアンカーの `responseTxDelayUus` を 1000 に下げた現在は
3ms になっている (5.2)。4 台分の測距時間の合計は約 12ms で、30Hz の周期 (33ms) の 4 割に収まる。

ここでいう 4 台分の測距時間は、1 測距の `elapsedMs` を 4 台ぶん足した値である。`elapsedMs` は `millis()` の
差で 1ms 刻みなので、±数 ms の精度しかない。1 スロット 8ms の 30Hz で、4 台 × 1980 回の測距がスロットの
遅れなしに回ったこと (5.2) が、1 台あたり 8ms 未満に収まっていることの裏付けになる。

巡回の周期そのものは、これとは別にタグの `CYCLE_STAT` (周期の先頭どうしの間隔) で実測している。周期は
1 周期を台数で等分したスロットの割り当てで決まり、10Hz で 100ms、30Hz で 32ms (スロットをミリ秒単位に
切り捨てるため) だった。当初の設定 (1 測距 6〜7ms) では、4 台分の測距時間は約 26ms と見積もられる。

### 5.2 削減すべきパラメータ

#### `resultRepeatCount = 3` + `resultRepeatGapMs = 3`

アンカーが Result フレームを 3 回送信する設定。タグは 1 回目で受信できれば抜けられるが、
**アンカー側は送り切るまで次の Poll を受けられない**ため、1 台あたり +6ms のビジー時間が生じる。
4 台巡回では無視できない。信頼性が確認できているなら `resultRepeatCount = 1` に落とす。ここが最大の削減余地。

実際に効いてくるのはビジー時間よりも、2 回目と 3 回目の Result が次のスロットの交信に重なることだった。
タグだけを 20Hz (1 スロット 12ms) にして試すと、特定のアンカー (0x0101 と 0x0103) で `RANGE_FRAME_MISMATCH` が
3〜9 割に達した。直前のスロットのアンカーが送った Result の再送を、タグが Response 待ちの間に受けている。
10Hz (1 スロット 25ms) では再送が次のスロットに届かないので起きない。10Hz を超えるには、
アンカー側で `resultRepeatCount` を 1 にすることが前提になる。

アンカー 4 台を `resultRepeatCount = 1` にして測ると、20Hz で 4 台 × 1160 回、30Hz で 4 台 × 1740 回の測距が
いずれも失敗 0 だった。10Hz でも失敗は増えておらず、再送を減らしたことによる取りこぼしは見えていない。

#### `responseTxDelayUus` と、タグの受信を始める時刻

アンカーは Poll の受信時刻から `responseTxDelayUus` 後に Response を遅延送信する。下限は `finalTxDelayUus` と
同じくホストの処理時間で決まる。3000 のままアンカー側の余裕 (`DS_RESP_STAT` の `min_margin_us`) を測ると、
Poll の受信から送信予約までは AtomS3 で 310〜325 µs、Atom Matrix で約 450 µs だった。1000 に下げると、
余裕は AtomS3 で 704〜715 µs、Atom Matrix で 546〜606 µs になり、1 測距は 5〜6ms から 3ms に縮んだ。

この値と組になるタグ側の設定が 2 つある。どちらもタグだけが使う。

- `responseRxAfterTxDelayUus` (1500 → 600): タグが Poll の送信完了から Response の受信を始めるまでの待ち。
  Response のプリアンブル (約 140 µs) が届く前に受信を始める必要がある。600 なら `responseTxDelayUus` が
  1000 のアンカーにも 3000 のアンカーにも間に合う (受信窓は 600 から `rxTimeoutUus` の 3000 までの間)
- `resultRxAfterFinalTxDelayUus` (500 → 0): タグが Final の送信完了から Result の受信を始めるまでの待ち。
  アンカーは Final を受けるとすぐに Result を送る。SPI を実際に 20MHz にしたアンカーでは Final の受信から
  送信開始まで 300 µs 程度しかなく、500 では受信を始める前に Result が終わってタグ側は 100% `RX_TIMEOUT` に
  なった (アンカー側は送信できているので成功と数える)。2MHz のころは 1ms 以上かかっていたので表に出なかった

この組み合わせのため、アンカーだけを新しいファームウェアにすると古いタグとは測距できない。書き換えるときは
タグを先にする。新しいタグは古いアンカーとも測距できる。

#### `hostTimeoutMs = 100` — 実用上の最大リスク

1 台が応答しなかった瞬間、そのサイクルに 100ms を消費する。30Hz (33ms) どころか 10Hz も割り込む。
遮蔽は必ず発生するため、これは「もし」ではなく「いつ」の問題である。
`hostTimeoutMs` は 1 測距の想定時間 + マージン (15〜20ms 程度) まで下げる。`rxTimeoutUus` も同様に見直す。

ライブラリを読むと、`hostTimeoutMs` は受信待ち 1 回ごとの上限で、実際の受信待ちはトランシーバーの
`rxTimeoutUus` で先に終わる。応答が無ければ Poll の送信から約 4.6ms で `RX_TIMEOUT` が返るので、
100ms を使い切るのはトランシーバーからの通知が来なかった場合に限られる。そこで次のようにした。

- タグの `hostTimeoutMs` は 10ms にした ([main_tag.cpp](../src/main_tag.cpp) の `TAG_HOST_TIMEOUT_MS`)。
  受信待ち 1 回は 5ms 以内に終わるので、保険として 2 倍の余裕を持たせた
- アンカーの `hostTimeoutMs` は 100ms のまま据え置く。アンカーでは Poll を待つ窓の長さも兼ねており、
  短くすると受信の張り直しが増えるだけで得るものがない
- `rxTimeoutUus` (3000) も据え置く。効くのは失敗したときだけで、そのときの所要時間 (約 4.6ms) は
  成功したときの所要時間より短く、周期を圧迫しない

#### `finalTxDelayUus` — 下限はホストの処理時間で決まる

Final は Response の受信時刻から `finalTxDelayUus` 後に遅延送信する。受信完了を検知してから送信を予約する
までに約 900 µs かかり、予約は送信時刻の約 200 µs 前までに済ませないと `TX_START_FAILED` になる。
1800 uus で残る余裕は約 700 µs だった。これ以上下げるには、先に SPI 転送の短縮が必要になる
(末尾の「参考: M5Stamp-UWB のフォーク」)。

受信時刻から送信予約までの時間を、トランシーバーのシステム時刻を途中で読んで分解した (AtomS3R のタグ)。

| 区間 | 当初 | SPI をまとめ転送 | 実際に 20MHz |
| --- | --- | --- | --- |
| 受信完了の検知 | — | 約 110 µs | 約 90 µs |
| フレーム長・受信データの読み出し | — | 約 230 µs | 約 80 µs |
| タイムスタンプ 2 個の読み出し | — | 約 130 µs | 約 55 µs |
| 遅延送信時刻と受信窓の設定 | — | 約 230 µs | 約 100 µs |
| 送信データと送信制御の書き込み | — | 約 210 µs | 約 60 µs |
| 合計 | 約 960 µs | 約 770 µs | 約 400〜450 µs |

「当初」の列は余裕の実測値からの逆算で、区間ごとの内訳は取っていない。まとめ転送にした後も、
レジスタ 1 回の読み書きに約 39 µs かかっており、そのうち約 27 µs が転送そのものだった。5 バイトの転送に
これだけかかるのは 2MHz 相当で、調べるとライブラリは初期化後も SPI を 2MHz のまま使っていた (5.3)。
フォークでこれを直すと、1 回は約 17 µs になった。内訳は転送が約 5 µs、`SPI.beginTransaction()` と
`endTransaction()` が合わせて約 10 µs で、残りがドライバの処理である。

これを受けて `finalTxDelayUus` を下げた。1000 では 4 台 × 520 回で失敗は無かったが、余裕の最小が 295 µs まで
下がる周期があった。2 ms ごとの最小値はほぼ 450 µs 以上なので、ときどき処理が遅れる要因 (割り込みなど) がある。
1200 に決め、10Hz で 4 台 × 1140 回を測って余裕の最小は 602 µs、`TX_START_FAILED` は 0 だった。
`finalTxDelayUus` を使うのはタグだけで、アンカーの Final の受信窓 (Response 送信の 500〜3500 uus 後) にも
収まるので、アンカーのファームを書き換えずに変えられる。1 測距は約 0.6 ms 縮んだ。

残る `beginTransaction()` と `endTransaction()` の約 10 µs (ミューテックスの取得と解放) は、交信 1 回の間
トランザクションを開いたままにすれば削れる。今の余裕では必要ないので手を付けていない。

#### シリアルログ

115200bps = 約 87µs/byte。現状の `DS_RESP_STAT` 行は 100 文字を超えており、**1 行で 8.7ms** を消費する。
30Hz (33ms 周期) で毎サイクル出力すると、それだけで予算の 1/4 が消える。

- 対策 1: `monitor_speed` を 921600 に引き上げる (1.1ms に短縮)
- 対策 2: 測位ループ中はログを間引く (現状の `LOG_INTERVAL` による間引きは正しい方向)

両方とも入れた。タグの `DS_RANGE_STAT` は試行回数ではなく時間で間引いて、周期によらずアンカーごとに
約 2 秒に 1 行にした。ESP32-S3 の USB シリアルはボーレートに関係なく速いので、ボーレートが効くのは UART で出す
旧世代 ESP32 (Atom Lite / Atom Matrix) の方である。

ボーレートは 921600 ではなく 1500000 にした ([host_init.cpp](../src/common/host_init.cpp) の `SERIAL_BAUD`)。
Atom Matrix の USB シリアル変換は FTDI (0403:6001) を名乗る M5Stack 独自のチップで、921600 では出力が
文字化けして読めなかった。24MHz を 16 で割った 1.5M の整数分の 1 しか正確に出せないとみられ、書き込みが
1500000 で通るのもそのためである。1500000 なら ESP32 側も分数分周で誤差 0.04% に収まり、1 行は 1ms 以下で出る。

同じ理由で、タグの LCD の書き換えも 200ms に 1 回までに抑えた。128x128 の全画面を送るのに 7ms 前後かかり、
その間は次のスロットを始められない。20Hz で毎周期書き換えていたときは、10 秒あたり約 40 回スロットの開始が
最大 3ms 遅れていた。

200ms に 1 回でも、30Hz (1 スロット 8ms) では測距の 3ms と合わせてスロットに収まらない。30Hz では 10 秒あたり
約 44 回 (書き換えの回数とほぼ同じ) スロットの開始が最大 3ms 遅れ、周期は 32〜35ms の間で揺れた。
揺れをなくすには、LCD への転送を測距ループの外 (Core 0 のタスクか DMA) へ出す必要がある。

そこで、転送を Core 0 のタスクに任せた ([status.cpp](../src/common/status.cpp) の `displayTaskMain()`)。
LCD は SPI3、UWB は SPI2 で別のバスなので、転送中も測距は止まらない。Core 1 は画面を描いてタスクを起こす
だけで戻る。送っている最中の面に次の画面を描かないよう、キャンバスを 2 面 (計 64 KB) 持ち、Core 1 は常に
裏面に描く。タスクは表と裏を入れ替えてから表を送り、送信中にもう 1 枚描き終えていれば最新の 1 枚だけを送る。
2 面目かタスクを用意できなかったときは、従来どおり Core 1 で直接送る (起動ログの `HOST` 行の
`display_push` が `task` か `direct` かで分かる)。DMA は M5GFX のトランザクションの扱いに踏み込む必要があり、
採らなかった。

30Hz で測り直すと、周期は 10 秒 × 5 回すべてで 32ms ちょうど、スロットの遅れは 0 になった
(4 台 × 1980 回で失敗は `RX_TIMEOUT` の 1 回)。この測定は Wi-Fi に接続し、テレメトリを送った状態で行った
(`batch_cycles = 4`)。10 秒ごとの 6 区間すべてで `CYCLE_STAT` は `wifi=OK` で、テレメトリは 10 秒あたり
約 78 パケットを送って送信失敗も捨てた周期も 0、`sendto()` の最大は 0.93ms だった。

### 5.3 SPI 速度

当初、Atom Lite (classic ESP32) は `config.spi_fast_hz = 8000000` に落としていた
(全信号が GPIO マトリクス経由となるため)。AtomS3 系の 16MHz に対してレジスタアクセスが 2 倍遅い。

その後、classic ESP32 と ESP32-S3 の両方を 20MHz に設定した
([src/common/hw_pins.h](../src/common/hw_pins.h) の `UWB_SPI_FAST_HZ`)。GPIO マトリクス経由の全二重転送の上限が
20MHz で、80MHz の APB クロックを割り切れる値でもある。起動時に 20MHz で ID レジスタを読み戻し、Atom Lite と
Atom Matrix の起動ログでも読み戻しが通ることを確認していた。

ところが、この設定は実際には効いていなかった。ライブラリは `spi_fast_hz` を受け取るが、初期化の途中で
高速レートへ切り替える処理を呼んでおらず、すべての転送を初期化時の `spi_slow_hz` (2MHz) で行っていた
(Qorvo のドライバが切り替えを呼ぶのは、このライブラリが使っていない初期化経路だけだった)。
起動時の読み戻しも 2MHz で行われていたので、何も確かめていなかった。8MHz に落としたときも
20MHz に上げたときも、実際の速度は同じ 2MHz である。

フォークで `dwt_initialise()` の直後に `spi_fast_hz` へ切り替えるように直した。レジスタ 1 回の読み書きは
約 39 µs から約 17 µs になった (5.2)。あわせて次のようにした。

- 起動時の読み戻しは 1 回ではなく 64 回続けて行う。タイミングの余裕が少ないと、失敗はときどきしか出ないため
- 読み戻しに失敗したら起動エラーにし、LCD に `E:SPI` (LED は赤) を出す。当初は 10MHz、2MHz の順に
  初期化し直していたが、5.2 の送受信タイミングは 20MHz での処理時間を前提に詰めてあり、遅いレートでは
  測距にならない。2MHz ではアンカーの Poll の受信から Response の予約までが約 1.3ms (3000 のときの余裕
  1779 µs からの逆算) で、`responseTxDelayUus` の 1000 に収まらない。10MHz は測っていない。IRQ 線の
  断線と同じく、故障として止めて気付けるようにした

AtomS3R のタグでは 20MHz で読み戻しが通り、10Hz で 4 台 × 1140 回の測距を失敗 2 回 (`RX_ERROR`) で終えた。
アンカーは AtomS3 (2 台)、AtomS3 Lite、Atom Matrix のいずれも 20MHz で読み戻しが通り、30Hz まで測距できた。
Atom Lite は Atom Matrix と同じ ESP32-PICO で UWB の配線も同じなので、Atom Matrix での確認をもって 20MHz で
動くものとし、個別の確認はしない。

- Atom Lite: 以前からアンカーとして運用しており、タグとしても動作することを確認した (2MHz)
- Atom Matrix: タグとアンカーの両方で動作することを確認した (2MHz)。アンカーは 20MHz でも確認した

AtomS3 Lite のアンカー (0x0102) だけ、`responseTxDelayUus` を 1000 にすると `TX_START_FAILED` が 8 割近く出た。
余裕は -257〜-139 µs で、Poll の受信の検知が最大 1 tick 遅れていた。IRQ 線 (G39) を読むと、割り込みを
すべて禁止しても High のままで、内部プルダウンを付けると Low になった。QM33120 が線を駆動しておらず、
つながっていない。拡大写真ではんだ付けに隙間が見つかった。IRQ 待ちのフォークは IRQ が来なくても 1 tick の
タイムアウトで回り続けるので、3000 の余裕では失敗にならず、これまで気付かなかった。はんだを直すまでの間は、
この 1 台を `-D M5STAMP_UWB_WAIT_MODE=1` (IRQ を使わず SYS_STATUS を読み続ける) でビルドして動かした。
その場合の余裕は 726〜743 µs で、IRQ 待ちの AtomS3 と変わらなかった。はんだを直して IRQ 待ちのビルドに戻すと、
余裕は 716〜727 µs になり、10Hz で約 620 回の失敗は 0 だった。

同じ故障に気付けるよう、フォークの `init()` で IRQ 線を検査し、QM33120 が線を駆動していなければ
`IRQ_LINE_FAULT` で初期化を失敗させるようにした。断線は故障なので、busy-poll に切り替えて動かし続けることは
しない。ファームウェアは SPI の速度を下げての再試行もせずに止まり、LCD に `E:IRQ` (LED は赤) を出す。
検査では線を 2 回読み、どちらも線が駆動されていなければホスト側のプルが勝つ向きにしてある。

- 割り込みをすべて禁止し、ホストのプルアップを付けて読む。正常なら 0
- QM33120 のタイマー (TIMER0) を満了させて割り込みを立て、ホストのプルダウンを付けて読む。正常なら 1。
  タイマーを使うので電波は出さない。`dwt_setinterrupt()` は許可したビットの状態を消去するので、
  タイマーを動かす前に許可しておく必要がある (逆にすると正常な基板でも 0 になった)

結果は起動ログの `UWB_IRQ,result=...,pin=...,idle=...,active=...` に出る。正常な AtomS3 (2 台)、AtomS3R の
タグ、Atom Matrix はいずれも `idle=0,active=1` だった。断線は、IRQ のピン番号を何もつながっていない
ピン (AtomS3 は G2、Atom Matrix は G26) に差し替えて再現し、どちらも `idle=1,active=0` で起動エラーに
なることを確かめた。はんだの隙間のような、接触が不安定な状態は再現できていない。

### 5.4 同時性誤差

当初の設定の見積もり (5.1) では 4 台巡回に 26ms かかり、最初と最後の測距で時刻が 26ms ずれる。
ローバーが 1m/s で走行する場合 2.6cm のズレとなる。この速度域では無視してよいが、
高速走行させる場合は効いてくる。FC の慣性情報で補間することで吸収できる。

フェーズ 3 の後は 1 測距 3ms、4 台分の測距時間の合計は約 12ms になった (5.1)。ただし実際の時刻のずれは、
測距にかかる時間ではなくスロットの割り当てで決まる。タグは 1 周期を台数で等分したスロットの先頭で
1 台ずつ測距するので、最初と最後の測距の間隔は 3 スロットぶんになる。4 台なら 10Hz (1 スロット 25ms) で
75ms、30Hz (1 スロット 8ms) で 24ms で、1m/s ではそれぞれ 7.5cm、2.4cm のずれになる。所要時間の 12ms
(1.2cm) まで縮めるには、スロットを周期の先頭に寄せて続けて測距する必要がある。

このずれが残るのは最小二乗の解 (3.6) である。フィルタ (3.7) は測距ごとにその時刻まで予測を進めてから
取り込むので、フィルタ後の位置には入らない。

### 5.5 結論

- **10Hz は確実に達成できる**。タグの既定の周期は 100ms (10Hz) にした
  ([main_tag.cpp](../src/main_tag.cpp) の `UWB_RANGE_CYCLE_MS`。ビルドフラグで変えられる)
- **30Hz は理論上ギリギリ届くが、当初の config (5.1 の表) のままでは不可能だった**。5.2 のパラメータ削減が前提
- 5.2 の削減を入れた結果、アンカー 4 台で **30Hz でも測距を続けられた**。1 測距 3ms、4 台分の測距時間は 12ms。
  失敗は 4 台 × 1740 回で 0 回、LCD の転送を移したあとの 4 台 × 1980 回で 1 回 (`RX_TIMEOUT`) だった。
  タグの LCD への転送を Core 0 へ移したので、30Hz でも周期は揺れない (5.2 の「シリアルログ」)
- 現実的には **10〜20Hz** を測位レートとし、FC 側の IMU/EKF で高レートに補間する構成を推奨
- UWB のレートを限界まで追うより、FC 側で慣性を積分し UWB で補正する方が滑らかで外れ値にも強い。
  UWB 測距が 1 周期落ちても位置推定を継続できる

当初は、まず `elapsedMs` の実測値が 6.5ms 前後に収まっているかを見て、30Hz が射程かどうかを判断する
つもりだった。実測は 6〜7ms で見積もりどおりで、5.2 の削減を入れて 3ms まで縮めたうえで、30Hz で測距を
続けられることを確かめた (フェーズ 3)。

## 6. IMU の扱い

Atom 内蔵 IMU は**使用しない**。ローバーにフライトコントローラを搭載しており、IMU はそちら側を使う。

参考: 現状のスケッチでは `cfg.internal_imu = false` としている。内部 I2C バスが UWB の RST / IRQ と
同じピンを使用するためであり、この設定は維持する。IMU をタグ側 Atom で使う必要がないため、
ピン競合の解決は不要となった。

タグ Atom と FC 間のインターフェース (UART / I2C / CAN 等) は別途検討する。

## 7. サーバー連携 (Wi-Fi)

### 7.1 データフロー

1. タグ起動 → Wi-Fi 接続
2. サーバーからアンカー座標表とバイアス補正値を取得 (HTTP/JSON を想定)
3. 取得したデータを NVS にキャッシュ
4. 以降の測位ループは Atom 内で完結。Wi-Fi が切断されても測位は継続
5. 走行中は測距結果と推定位置をサーバーへ送り続ける (デバッグ用のテレメトリ。UDP)

測位の計算自体はサーバーに依存しない。テレメトリが届かなくても走行には影響しない。

### 7.2 取得するデータ

```json
{
  "rev": 7,
  "pan_id": "0xDECA",
  "bias_mm": 0,
  "anchors": [
    { "id": "0x0100", "x": 0.000, "y": 0.000, "z": 1.800 },
    { "id": "0x0101", "x": 5.120, "y": 0.000, "z": 1.800 },
    { "id": "0x0102", "x": 5.080, "y": 4.310, "z": 1.800 },
    { "id": "0x0103", "x": 0.030, "y": 4.290, "z": 1.800 }
  ]
}
```

`id` は 2.2 の採番どおり UWB の `responderAddress` そのものである。アドレスを別フィールドに分けると
二重管理になるため持たせない。

サーバー側の詳細 (エンドポイント、データベース、テレメトリの受信) は
[server-design.md](server-design.md) にまとめる。本節は**タグから見た取得内容**のみを扱う。

### 7.3 NVS キャッシュの必要性

サーバーが落ちている、あるいは Wi-Fi が繋がらない状態でもローバーを動かせるようにするため、
取得済みの座標表は NVS に保存する。起動時はまずサーバーへ問い合わせ、失敗したらキャッシュにフォールバックする。
キャッシュも無い場合のみ測位不能として扱う。

### 7.4 Wi-Fi と UWB の同時動作 — 一部検証済み

ESP32 の Wi-Fi タスクは比較的高い優先度で動作し、CPU を占有する時間帯がある。
一方 `respondDSRange()` / `requestDSRange()` の待機ループは `delay(1)` でポーリングしている
(`receiveFrame()` の実装と同様の構造)。これは当初の上流ライブラリの話で、現在のフォークは IRQ で待つ
(末尾の「参考: M5Stamp-UWB のフォーク」)。

DS-TWR のフレーム送信タイミング自体は QM33120 チップ内部でハードウェア的にスケジュールされるため、
ホスト側の遅延がただちに測距精度を壊すわけではない。しかし、

- ホストのポーリングが Wi-Fi タスクに阻害され、受信完了の検出が遅れる
- 結果として `hostTimeoutMs` に達し、測距失敗としてカウントされる

という経路で**測位レートに影響する可能性がある**。

検証済みの範囲と、残っている範囲は次のとおり。いずれも測距の周期とスロットの遅れを見たものである。

- 5Hz: Wi-Fi 未設定、認証に失敗して再接続を繰り返す状態、接続中でテレメトリを送る状態、AP を落とした状態の
  4 つで、周期とスロットの遅れに影響が無いことを確かめた ([server-design.md](server-design.md) の 7.1)
- 10Hz / 30Hz: 接続中でテレメトリを送る状態で、周期はすべて設定どおり (100ms / 32ms)、スロットの遅れは 0
  だった (5.2、server-design.md の 7.1)
- 10Hz / 30Hz で測位 (3.6) の計算を載せた状態: 接続中でテレメトリを送る状態で、周期は設定どおり、スロットの
  遅れは 0 だった。計算時間は最大 116 µs (server-design.md の 7.1)
- 未確認: 10Hz 以上での AP の切断と再接続

#### 方針: Wi-Fi は常時接続とする (決定)

デバッグのためにテレメトリを継続送信するため、**走行中も Wi-Fi は切らない**。
「座標表の取得後に `WiFi.mode(WIFI_OFF)` する」案は採らない。テレメトリが取れなくなり、
可視化による精度評価が成立しないためである。

そのうえで、レートへの影響は以下で抑え込む。詳細は [server-design.md](server-design.md) の 7.1 に書く。

- UWB 測距タスクを Core 1 に固定する (ESP32-S3 はデュアルコア。Wi-Fi は通常 Core 0)
- 送信は複数サイクルをまとめて UDP 1 発にし、巡回の先頭スロット直前に行う。測距と測距の間に割り込ませない
- Wi-Fi の再接続処理で測位ループをブロックしない

影響の大きさは実測で確認する。許容できない場合でも Wi-Fi を切るのではなく、
送信頻度を下げる方向で調整する。

## 参考: 確認済みのライブラリ挙動

`m5stack/M5Stamp-UWB` について、本検討にあたり確認した事項。

- `respondDSRange()` は `dst != responderAddress` のフレームを破棄する。ブロードキャスト受信は非対応。
  Poll 待ちで破棄した場合も受信は続けず、`RangeFrameMismatch` を返す。このとき `txMarginUs` は未設定のまま
- `receiveFrame()` はアドレスフィルタを行わない。`src` / `dst` は `M5Stamp_UWBRxResult` として返る
- `M5Stamp_UWBFrameConfig.dst` のデフォルトは `0xFFFF` (ブロードキャスト)
- `requestDSRange()` / `respondDSRange()` は config を引数で受け取り、内部に役割状態を持たない。
  同一機体で initiator / responder を動的に切り替え可能
- `M5Stamp_UWBDSResponderResult.requester` には Poll 送信元アドレスが入る。
  Poll 未受信時は 0 のままで、非ゼロなら Poll/Response は成立して Final が失われたことを意味する
- SYS_STATUS のポーリングは、読み出しの間に `delay(1)` を挟む。受信の検知が次の FreeRTOS tick まで遅れる
  (次節)
- 遅延送信の成否は、`dwt_starttx()` が開始コマンドの直後に SYS_STATUS の HPDWARN を読んで判定する。
  ライブラリは HPDWARN をクリアしないが、次の交信には残らない (失敗直後の 1018 回すべてで確認)

## 参考: M5Stamp-UWB のフォーク

ライブラリは上流の `m5stack/M5Stamp-UWB` ではなく、フォーク
[8ga3/M5Stamp-UWB](https://github.com/8ga3/M5Stamp-UWB) の `irq-wait` ブランチを、コミットで固定して使う
([platformio.ini](../platformio.ini) の `lib_deps`)。2026-09-27 に切り替えた。

### 経緯

アンカー 1〜4 台のどの構成でも、タグの測距が `TX_START_FAILED` で約 17% 失敗していた。
失敗していたのは Final の遅延送信 (`dwt_starttx(DWT_START_TX_DELAYED)`) である。

- Final は、Response の受信時刻から `finalTxDelayUus` (1800 uus) 後に送信するよう予約する
- 上流は受信完了を `delay(1)` を挟んだポーリングで待つため、受信の検知が次の FreeRTOS tick まで遅れる
- 検知から予約までの SPI 転送に約 900 µs かかり、予約は送信時刻の約 200 µs 前までに済ませる必要がある。
  これに tick 待ちの遅れ (最大 1 ms) が加わると間に合わない
- 遅れの大きさは、交信と tick の位相で決まる。タグは `millis()` の区切りで測距を始めるので、位相は
  `millis()` と tick の位相差、つまり起動にかかる時間で決まる。同じバイナリなら再起動しても変わらない。
  そのため、測距と関係のない変更でも失敗率が 0% から 100% の間で振れた

### 検証

測距の開始を 0〜900 µs の範囲で 100 µs ずつずらし、各段階で 200 回ずつ試行した
(AtomS3 のタグ、アンカー 4 台、`finalTxDelayUus` = 1800)。余裕時間は、遅延送信を予約した時点で
送信時刻まで残っていた時間である。

| 待ち方 | 余裕時間 | 失敗 |
| --- | --- | --- |
| `delay(1)` (上流) | -237〜944 µs。開始のずれに対して周期 1 ms で変わる | 段階により 0〜100% |
| IRQ 割り込み (フォーク) | 705〜947 µs。開始のずれによらずほぼ一定 | 2400 回中 0 回 |

`delay(1)` で失敗した 1018 回の余裕時間は最大 202 µs で、約 200 µs が成否の境目になる。
プリアンブルと SFD の送信時間 (約 136 µs) に、予約後の SPI 転送の時間を足した値と合う。

### フォークの変更点

- `M5STAMP_UWB_WAIT_MODE` で待ち方を選ぶ (0 = `delay(1)`、1 = busy-poll、2 = IRQ。既定は 2)。
  2 は RXFCG・RX タイムアウト・RX エラーだけを IRQ ピンへ出し、ISR からのタスク通知で起きる。
  TXFRS を含めないのは、Poll の送信完了から Response の処理まで立ったままになり、RXFCG の立ち上がりを
  取りこぼすためである。通知の待ちは 1 tick でタイムアウトするので、取りこぼしても上流と同じ遅れで済む
- DS-TWR の結果に `txMarginUs` (上記の余裕時間) を加えた。タグでは Final、アンカーでは Response の値になる。
  `M5STAMP_UWB_MEASURE_MARGIN=0` を指定すると、計測のための SYS_TIME の読み出しを外せる
- `dwt_initialise()` の直後に SPI を `spi_fast_hz` へ切り替える。上流はこの切り替えをしておらず、
  すべての転送が `spi_slow_hz` (2MHz) で行われていた (5.3)
- SPI の転送を 1 バイトずつの `transfer()` から、最大 64 バイトずつの `transferBytes()` / `writeBytes()` に
  まとめた。Arduino-ESP32 のこれらの関数はバッファを 32 ビット単位で読み書きするので、4 バイト境界に
  揃えた作業用バッファを経由する

ファームウェアは、余裕時間の最小値を `DS_RANGE_STAT` / `DS_RESP_STAT` の `min_margin_us` に、失敗時の値を
`DS_RANGE_FAIL` の `margin_us` に出力する。起動時の `UWB_TIMING` で `finalTxDelayUus` と待ち方を確認できる
([src/common/uwb_link.cpp](../src/common/uwb_link.cpp))。

### 未確認の事項と今後

  `beginTransaction` と CS の `digitalWrite` を行っていた。その後、まとめ転送と 20MHz への切り替えで
  約 400〜450 µs に縮め、`finalTxDelayUus` を 1200 に下げた (5.2)。この項目は対応済み
