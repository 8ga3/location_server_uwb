# マルチアンカー UWB 測位システム 設計メモ

M5Stamp-UWB (QM33120) を用いた DS-TWR 測距を、単一ペアからマルチアンカー測位へ拡張するための設計検討。
対象は Atom S3 / Atom S3 Lite / Atom Lite / Atom Matrix + M5Stamp-UWB。ライブラリは `m5stack/M5Stamp-UWB` を、
受信待ちを IRQ 割り込みにしたフォークで使う (末尾の「参考: M5Stamp-UWB のフォーク」)。

- 作成日: 2026-09-21
- 想定用途: ローバー型ラジコンの自己位置推定
- 現状: タグ 1 台 ⇔ アンカー 1 台の DS-TWR が動作済み

---

## 1. システム構成

```text
  [アンカー 0..N-1]        [タグ (ローバー搭載)]        [サーバー]
   M5Stamp-UWB             M5Stamp-UWB + Atom            アンカー座標表
   固定設置                 + フライトコントローラ          を保持
        |                          |                          |
        +----- UWB DS-TWR ---------+                          |
                                   +------- Wi-Fi ------------+
                                     起動時に座標表を取得
```

### 役割分担

| 要素 | 責務 |
| --- | --- |
| アンカー | UWB responder。固有 ID のみ保持。座標は持たない |
| タグ | UWB initiator。全アンカーを巡回測距 → 三辺測量で自己位置を算出 |
| サーバー | アンカー座標表とバイアス補正値を保持。タグへ配布 |
| FC (フライトコントローラ) | IMU による姿勢・慣性。Atom 内蔵 IMU は使用しない |

**測位計算はタグ側の Atom 内で実行する。** サーバーからは座標表を起動時に 1 度取得するだけで、
以降の測位ループはオフラインで完結する。Wi-Fi が切れても測位は継続できる。

## 2. アンカーアドレスの割り当て

### 2.1 制約

ライブラリの `respondDSRange()` は、受信フレームの `dst != responderAddress` の場合そのフレームを破棄する
(`.pio/libdeps/*/M5Stamp_UWB/src/M5Stamp_UWB.cpp` の該当箇所)。ブロードキャスト受信には対応していない。
したがって**アンカーごとにユニークな `responderAddress` が必須**である。

ただし、ここでいう「破棄」は受信を続けることではない。Poll を待っている間に自機宛てでないフレーム
(他アンカー宛ての Poll や、タグと他アンカーの間の Response / Final) を受けると、`respondDSRange()` は
そのフレームを捨てたうえで `RangeFrameMismatch` を返して終わる。複数アンカー構成では毎周期起きることなので、
呼び出し側はこれを失敗として扱わず、無通信 (NO POLL) と同じく次の `respondDSRange()` へ進む。
Final を待っている間の不一致は本当の異常なので、こちらは失敗として扱う。
両者は `txMarginUs` で見分ける。この値は Response の送信を予約した時点で入るため、未設定なら Poll 待ちでの
不一致である (実装は [main_anchor.cpp](../src/main_anchor.cpp) の `runResponder()`)。

また Poll フレームの宛先はタグ側が指定するため、**タグは各アンカーのアドレスを事前に知っている必要がある**。
このため「MAC アドレス下位 16bit を自動採番」のような方式は単体では成立しない (タグが知り得ない)。

### 2.2 採用方針 (実装済み)

16bit ショートアドレスを役割ごとの範囲に分け、**アドレスそのものを機体の ID として直接持たせる**。
別のオフセット値を介さないため、ログに出るアドレスと設定した ID が常に一致する。

```text
panId             = 0xDECA              (全機共通)
タグ              = 0x0001..0x00FF      (initiatorAddress)
アンカー          = 0x0100..0xFFFE      (responderAddress)
```

- タグは当面 1 台だが、下り TDoA (`downlink-tdoa-design.md`) では多数のタグが前提になるため 255 台分を予約しておく
- `0xFFFF` は 802.15.4 のブロードキャストアドレスなので、アンカーの上限は `0xFFFE`
- アドレスの上位側を見るだけでタグかアンカーかが判別でき、ID 空間が衝突しない

この設計により以下が成立する。

- タグはアンカー ID の一覧を順に叩くだけで全アンカーを巡回できる
- 巡回が実質的に TDMA として機能し、アンカー間の衝突が発生しない
- ライブラリの responder は受信フレームの `dst` と `panId` しか照合しない (`src` は見ない) ため、
  アンカー側はタグ ID を知らなくてよい。応答は常に Poll の送信元へ返される

タグが巡回するアンカー ID の一覧は、**起動時に測位サーバーから設置座標とあわせて取得する** (第 7 節 /
[server-design.md](server-design.md) 5.1)。取得した構成は NVS へキャッシュし、サーバーへ届かないときは
キャッシュで動作する。キャッシュも無い場合は巡回先が決まらないため測距を開始しない。

### 2.3 ID の設定方法 (実装済み)

ソースコードを直接書き換えて台数分ビルドする方式は避ける。以下を採用する。

#### 採用方式: NVS (Preferences) 保存 + 起動時のシリアル入力

当初検討した「ボタン長押しでインクリメント」方式は、画面のない Atom Lite / AtomS3 Lite では
現在値を提示できず (LED 1 個で 4 台以上の ID を表現できない)、採番 UI として成立しないため採用しない。
ボタンは**設定モードへ入るトリガのみ**に使う。

- 全機に同一ファームウェアをフラッシュする
- NVS namespace `uwb` / key `id` に 16bit で保存。再フラッシュしても保持される (`erase_flash` を実行しない限り)
- 起動時、ID が未設定 (または役割の範囲外) ならシリアル入力を待つ。**10 進数**で入力し、
  範囲外や数字以外は `ID_INPUT,result=ERR` を返して再要求する
- 入力待ちの表示: 画面のある AtomS3 は LCD に `SET ID` と入力中の値、画面のない Lite 系は
  **LED マゼンタ点灯**。マゼンタは通常動作の RED / YELLOW / GREEN と重ならないので一目で判別できる。
  Atom Matrix は 5x5 の LED をすべてマゼンタで点ける (通常動作中は状態の色で自機の ID を表示する)
- 電源投入またはリセット直後に本体ボタンが押されていれば、設定済みでも設定モードへ入る (現場での振り直し)
- 起動時ログに `DEVICE_ID,role=...,id=...,source=nvs|serial` を必ず出力する

シリアル入力を待つ間は UWB を初期化しない。ID が決まる前に電波を出さないためである。

実装はタグとアンカーで共通の [src/common/device_id.h](../src/common/device_id.h)。ボタンのピンは LED と同じ理由で
`getBoard()` ではなくビルドターゲットから決める (AtomS3 系 G41 / Atom Lite と Atom Matrix G39)。

## 3. 測位の原理と必要台数

### 3.1 測距と測位の区別

DS-TWR が返すのは距離スカラーのみである。座標を得るには、**既知のアンカー座標**と組み合わせた三辺測量が必要になる。
アンカー配置が事前に既知であることは、計算をどこで行うかに関わらず前提となる。

### 3.2 座標系

相対座標でよく、絶対座標や方位は不要。アンカー 0 を原点、アンカー 0→1 方向を X 軸に取るのが定石。
ただし**スケールは実寸**が必要なので、アンカー間距離は実測値を用いる。

### 3.3 必要台数 (測位側)

DS-TWR は真の距離を返すため、時刻バイアスの未知数が不要。

- **2D 測位 (高さ既知): 未知数 2 → 3 台で一意、4 台で冗長 1**
- 3D 測位: 未知数 3 → 4 台で一意、5 台で冗長 1

重要なのは「設置台数」ではなく「**その瞬間に見えている台数**」である。4 台設置でも遮蔽により 3 台しか届かなければ
冗長ゼロ、2 台なら測位不能となる。ローバーの場合、車体自身や障害物による遮蔽が発生しうる。

### 3.4 配置 (GDOP)

- アンカーを一直線または一直線に近い形に配置すると、解が極端に不安定になる
- 測距誤差 10cm が位置誤差 1m 級に増幅されうる
- 4 台なら**正方形に近い配置**とし、タグ (ローバー) は 4 台が作る四角形の**内側**を走行させる
- 四角形の外に出ると精度が急落する

### 3.5 初期方針

**2D 測位・アンカー 4 台・座標は手測り**から開始する。

- 高さは全アンカー同一とし、2D 問題として解く
- ローバーは地上を走るため高さ方向の変動が小さく、2D で十分
- 自動推定 (self-survey) は後述するが、初期段階では手測りで確実に動かす

## 4. アンカー座標の自動推定 (self-survey) — 将来の拡張

手測りが動作した後の拡張として検討する。

### 4.1 ライブラリ側の実現可能性 (確認済み)

- `receiveFrame()` はアドレスフィルタを一切行わない。`src` / `dst` は結果として返るのみ。
  → 任意の制御メッセージの受信に使える
- `M5Stamp_UWBFrameConfig.dst` のデフォルトは `0xFFFF` (ブロードキャスト)
- `requestDSRange()` / `respondDSRange()` は毎回 config を引数で受け取り、内部に役割状態を持たない。
  → **同一機体で呼び分けるだけで initiator / responder を切り替えられる**

### 4.2 手順

#### フェーズ 0: サーベイモード起動

通常の responder ループを抜けて survey モードへ入る。トリガはボタン長押しまたはシリアルコマンド。

#### フェーズ 1: 相互測距

1. マスター 1 台 (アンカー 0 で固定してよい) がブロードキャストで `ROUND=i` を告知する
2. `anchorId == i` の機体が initiator となり、`responderAddress` を書き換えながら j = 0..N-1 (j≠i) を順に `requestDSRange()`
3. **それ以外の全機体は `respondDSRange()` を回しっぱなしにする。** 自分宛でないフレームは dst 不一致で破棄されるため、調停は不要。
   このとき返る `RangeFrameMismatch` は失敗として扱わない (2.1 節)
4. ラウンド完了後 `DONE` をブロードキャストし、マスターが `ROUND=i+1` へ進める

両方向 (i→j と j→i) を測定して平均すると、アンテナ遅延の非対称性が均される。
各ペア 20 回程度測定し**中央値**を採ってマルチパス外れ値を除去する。

#### フェーズ 2: 距離行列の集約

各 initiator が `D,i=0,j=3,mm=4213` 形式でシリアル出力する。マスター 1 台を PC に接続し、
ブロードキャストで報告を集めて一括出力する方式でもよい。

#### フェーズ 3: 座標計算 (PC 上で実行。ESP32 で行う必要はない)

1 回限りの作業なので Python が適している。

古典的 MDS で初期解を得る。

1. 対称化: `d_ij = (d_ij + d_ji) / 2` として N×N 距離行列 D を構成
2. 二重中心化: `J = I - (1/N) * ones((N,N))` として `B = -0.5 * J @ (D**2) @ J`
3. B を固有分解し、固有値の大きい順に k 個 (2D なら k=2) を取る
4. `X = V_k @ sqrt(diag(lambda_k))` が初期座標 (N×k)

次に非線形最小二乗で精密化する (`scipy.optimize.least_squares`)。

残差を `r_ij = ||x_i - x_j|| + b - d_ij` と定義して最小化する。
`b` はアンテナ遅延由来の共通オフセットであり、**未知数に加えて同時推定する**のが要点。
ここで得た `b` はタグ測位時の距離にも同様に効くため、補正値として保存しサーバー側で配布する。

#### フェーズ 4: ゲージ固定

MDS の解は並進・回転・鏡映が自由なので固定する (2D の場合)。

1. 平行移動: アンカー 0 を原点へ移す
2. 回転: アンカー 1 が +X 軸上に来るよう全体を回転
3. 鏡映: アンカー 2 の y が正になるよう、必要なら y の符号を反転

これで数値的には一意に定まる。ただし**実世界のどちら向きかは決まらない**。
「アンカー 2 は実際に 0→1 方向から見て左か右か」の 1bit だけは人が目視で判断する必要がある。ここは自動化できない。

#### フェーズ 5: 検証

- **残差 RMS**: 数 cm〜10cm 程度なら妥当。それ以上なら遮蔽や NLOS を疑う
- **スケール照合**: 1〜2 辺をメジャーで実測して比較する。系統的にずれていればバイアス `b` の推定が効いていない
- **固有値チェック**: 2D なら λ3 が λ1, λ2 に対して十分小さいこと。大きければ配置が平面でない

### 4.3 self-survey に必要な台数

2D で自由度を数える。

- 未知数: N 点 × 2 = `2N`、ゲージ固定で −3 (並進 2 + 回転 1)、バイアス b を +1 → **2N − 2**
- 観測数: ペア数 = **N(N−1)/2** (両方向は平均するため 1 ペア 1 拘束)

| N | 観測数 | 有効未知数 | 冗長度 |
| --- | --- | --- | --- |
| 3 | 3 | 4 | 解けない (b を諦めれば辛うじて一意) |
| 4 | 6 | 6 | **0 — 一意だが自己検証不能** |
| 5 | 10 | 8 | 2 |
| 6 | 15 | 10 | 5 |

**N=4 では残差が常に 0 になる。** 測距が 1 本ずれていても、それを吸収する形に座標が動くだけなので、
残差からは異常を検出できない。

注意: 各ペアを 20 回測定しても幾何的な冗長性は増えない。繰り返しはノイズ平均化にしか効かず、
形の拘束数は**ペア数のみ**で決まる。

結論として、**self-survey を検証込みで運用するには 5 台以上が必要**。
4 台で self-survey を試すこと自体は構わないが、必ず手測り値と突き合わせること。

### 4.4 高さ (Z) の扱い

**アンカーを全て同じ高さに設置すると、相互測距だけでは Z が決まらない** (同一平面の退化)。
「2D は自動推定、高さは手測り」を推奨する。3D を自動化する場合は、数台を意図的に異なる高さに設置する必要がある。

### 4.5 運用上の注意

- survey 中の見通しは必須。遮蔽されたペアは系統的に長い距離として出る。残差の大きいペアは除外して再計算する
- アンカーを移設するたびに survey を再実行する。ボタン起動にしておくと現場で回せる

## 5. 測位レートの検討

目標: **最低 10Hz、可能なら 30Hz**。

### 5.1 時間予算

`M5Stamp_UWBDSRangeConfig` ([uwb_link.cpp](../src/common/uwb_link.cpp) の `initUwb()`) で DS-TWR 1 回を積算する。
uus (UWB microsecond) ≈ 1.0256µs。当初の設定値で見積もった。

| 項目 | 設定値 | 実時間 |
| --- | --- | --- |
| `responseTxDelayUus` | 3000 uus | 3.08ms |
| `finalTxDelayUus` | 1800 uus | 1.85ms |
| `resultRxAfterFinalTxDelayUus` | 500 uus | 0.51ms |
| フレーム空中時間 (4 本) | — | 約 1ms |
| **合計 (支配項)** | | **約 6.5ms / 測距** |

4 アンカー巡回で 26ms ≈ 38Hz。数値上は 30Hz に乗るが余裕はない。

実測では、タグ側の `elapsedMs` (Poll の送信から距離通知の受信まで) は 6〜7ms で見積もりどおりだった。
`finalTxDelayUus` を 1200 に下げると 5〜6ms、さらにアンカーの `responseTxDelayUus` を 1000 に下げた現在は
3ms になっている (5.2)。4 アンカー巡回で 12ms で、30Hz の周期 (33ms) の 4 割に収まる。

### 5.2 削減すべきパラメータ

#### `resultRepeatCount = 3` + `resultRepeatGapMs = 3`

アンカーが Result フレームを 3 回送信する設定。タグは 1 回目で受信できれば抜けられるが、
**アンカー側は送り切るまで次の Poll を受けられない**ため、1 台あたり +6ms のビジー時間が生じる。
4 台巡回では無視できない。信頼性が確認できているなら `resultRepeatCount = 1` に落とす。ここが最大の削減余地。

実際に効いてくるのはビジー時間よりも、2 回目と 3 回目の Result が次のスロットの交信に重なることだった。
タグだけを 20Hz (1 スロット 12ms) にして試すと、特定のアンカー (0x0101 と 0x0103) で `RANGE_FRAME_MISMATCH` が
3〜9 割に達した。直前のスロットのアンカーが送った Result の再送を、タグが Response 待ちの間に受けている。
10Hz (1 スロット 25ms) では再送が次のスロットに届かないので起きない。10Hz を超えるには、
アンカー側で `resultRepeatCount` を 1 にすることが前提になる。

アンカー 4 台を `resultRepeatCount = 1` にして測ると、20Hz で 4 台 × 1160 回、30Hz で 4 台 × 1740 回の測距が
いずれも失敗 0 だった。10Hz でも失敗は増えておらず、再送を減らしたことによる取りこぼしは見えていない。

#### `responseTxDelayUus` と、タグの受信を始める時刻

アンカーは Poll の受信時刻から `responseTxDelayUus` 後に Response を遅延送信する。下限は `finalTxDelayUus` と
同じくホストの処理時間で決まる。3000 のままアンカー側の余裕 (`DS_RESP_STAT` の `min_margin_us`) を測ると、
Poll の受信から送信予約までは AtomS3 で 310〜325 µs、Atom Matrix で約 450 µs だった。1000 に下げると、
余裕は AtomS3 で 704〜715 µs、Atom Matrix で 546〜606 µs になり、1 測距は 5〜6ms から 3ms に縮んだ。

この値と組になるタグ側の設定が 2 つある。どちらもタグだけが使う。

- `responseRxAfterTxDelayUus` (1500 → 600): タグが Poll の送信完了から Response の受信を始めるまでの待ち。
  Response のプリアンブル (約 140 µs) が届く前に受信を始める必要がある。600 なら `responseTxDelayUus` が
  1000 のアンカーにも 3000 のアンカーにも間に合う (受信窓は 600 から `rxTimeoutUus` の 3000 までの間)
- `resultRxAfterFinalTxDelayUus` (500 → 0): タグが Final の送信完了から Result の受信を始めるまでの待ち。
  アンカーは Final を受けるとすぐに Result を送る。SPI を実際に 20MHz にしたアンカーでは Final の受信から
  送信開始まで 300 µs 程度しかなく、500 では受信を始める前に Result が終わってタグ側は 100% `RX_TIMEOUT` に
  なった (アンカー側は送信できているので成功と数える)。2MHz のころは 1ms 以上かかっていたので表に出なかった

この組み合わせのため、アンカーだけを新しいファームウェアにすると古いタグとは測距できない。書き換えるときは
タグを先にする。新しいタグは古いアンカーとも測距できる。

#### `hostTimeoutMs = 100` — 実用上の最大リスク

1 台が応答しなかった瞬間、そのサイクルに 100ms を消費する。30Hz (33ms) どころか 10Hz も割り込む。
遮蔽は必ず発生するため、これは「もし」ではなく「いつ」の問題である。
`hostTimeoutMs` は 1 測距の想定時間 + マージン (15〜20ms 程度) まで下げる。`rxTimeoutUus` も同様に見直す。

ライブラリを読むと、`hostTimeoutMs` は受信待ち 1 回ごとの上限で、実際の受信待ちはトランシーバーの
`rxTimeoutUus` で先に終わる。応答が無ければ Poll の送信から約 4.6ms で `RX_TIMEOUT` が返るので、
100ms を使い切るのはトランシーバーからの通知が来なかった場合に限られる。そこで次のようにした。

- タグの `hostTimeoutMs` は 10ms にした ([main_tag.cpp](../src/main_tag.cpp) の `TAG_HOST_TIMEOUT_MS`)。
  受信待ち 1 回は 5ms 以内に終わるので、保険として 2 倍の余裕を持たせた
- アンカーの `hostTimeoutMs` は 100ms のまま据え置く。アンカーでは Poll を待つ窓の長さも兼ねており、
  短くすると受信の張り直しが増えるだけで得るものがない
- `rxTimeoutUus` (3000) も据え置く。効くのは失敗したときだけで、そのときの所要時間 (約 4.6ms) は
  成功したときの所要時間より短く、周期を圧迫しない

#### `finalTxDelayUus` — 下限はホストの処理時間で決まる

Final は Response の受信時刻から `finalTxDelayUus` 後に遅延送信する。受信完了を検知してから送信を予約する
までに約 900 µs かかり、予約は送信時刻の約 200 µs 前までに済ませないと `TX_START_FAILED` になる。
1800 uus で残る余裕は約 700 µs だった。これ以上下げるには、先に SPI 転送の短縮が必要になる
(末尾の「参考: M5Stamp-UWB のフォーク」)。

受信時刻から送信予約までの時間を、トランシーバーのシステム時刻を途中で読んで分解した (AtomS3R のタグ)。

| 区間 | 当初 | SPI をまとめ転送 | 実際に 20MHz |
| --- | --- | --- | --- |
| 受信完了の検知 | — | 約 110 µs | 約 90 µs |
| フレーム長・受信データの読み出し | — | 約 230 µs | 約 80 µs |
| タイムスタンプ 2 個の読み出し | — | 約 130 µs | 約 55 µs |
| 遅延送信時刻と受信窓の設定 | — | 約 230 µs | 約 100 µs |
| 送信データと送信制御の書き込み | — | 約 210 µs | 約 60 µs |
| 合計 | 約 960 µs | 約 770 µs | 約 400〜450 µs |

「当初」の列は余裕の実測値からの逆算で、区間ごとの内訳は取っていない。まとめ転送にした後も、
レジスタ 1 回の読み書きに約 39 µs かかっており、そのうち約 27 µs が転送そのものだった。5 バイトの転送に
これだけかかるのは 2MHz 相当で、調べるとライブラリは初期化後も SPI を 2MHz のまま使っていた (5.3)。
フォークでこれを直すと、1 回は約 17 µs になった。内訳は転送が約 5 µs、`SPI.beginTransaction()` と
`endTransaction()` が合わせて約 10 µs で、残りがドライバの処理である。

これを受けて `finalTxDelayUus` を下げた。1000 では 4 台 × 520 回で失敗は無かったが、余裕の最小が 295 µs まで
下がる周期があった。2 ms ごとの最小値はほぼ 450 µs 以上なので、ときどき処理が遅れる要因 (割り込みなど) がある。
1200 に決め、10Hz で 4 台 × 1140 回を測って余裕の最小は 602 µs、`TX_START_FAILED` は 0 だった。
`finalTxDelayUus` を使うのはタグだけで、アンカーの Final の受信窓 (Response 送信の 500〜3500 uus 後) にも
収まるので、アンカーのファームを書き換えずに変えられる。1 測距は約 0.6 ms 縮んだ。

残る `beginTransaction()` と `endTransaction()` の約 10 µs (ミューテックスの取得と解放) は、交信 1 回の間
トランザクションを開いたままにすれば削れる。今の余裕では必要ないので手を付けていない。

#### シリアルログ

115200bps = 約 87µs/byte。現状の `DS_RESP_STAT` 行は 100 文字を超えており、**1 行で 8.7ms** を消費する。
30Hz (33ms 周期) で毎サイクル出力すると、それだけで予算の 1/4 が消える。

- 対策 1: `monitor_speed` を 921600 に引き上げる (1.1ms に短縮)
- 対策 2: 測位ループ中はログを間引く (現状の `LOG_INTERVAL` による間引きは正しい方向)

両方とも入れた。タグの `DS_RANGE_STAT` は試行回数ではなく時間で間引いて、周期によらずアンカーごとに
約 2 秒に 1 行にした。ESP32-S3 の USB シリアルはボーレートに関係なく速いので、ボーレートが効くのは UART で出す
旧世代 ESP32 (Atom Lite / Atom Matrix) の方である。

ボーレートは 921600 ではなく 1500000 にした ([host_init.cpp](../src/common/host_init.cpp) の `SERIAL_BAUD`)。
Atom Matrix の USB シリアル変換は FTDI (0403:6001) を名乗る M5Stack 独自のチップで、921600 では出力が
文字化けして読めなかった。24MHz を 16 で割った 1.5M の整数分の 1 しか正確に出せないとみられ、書き込みが
1500000 で通るのもそのためである。1500000 なら ESP32 側も分数分周で誤差 0.04% に収まり、1 行は 1ms 以下で出る。

同じ理由で、タグの LCD の書き換えも 200ms に 1 回までに抑えた。128x128 の全画面を送るのに 7ms 前後かかり、
その間は次のスロットを始められない。20Hz で毎周期書き換えていたときは、10 秒あたり約 40 回スロットの開始が
最大 3ms 遅れていた。

200ms に 1 回でも、30Hz (1 スロット 8ms) では測距の 3ms と合わせてスロットに収まらない。30Hz では 10 秒あたり
約 44 回 (書き換えの回数とほぼ同じ) スロットの開始が最大 3ms 遅れ、周期は 32〜35ms の間で揺れた。
揺れをなくすには、LCD への転送を測距ループの外 (Core 0 のタスクか DMA) へ出す必要がある。

### 5.3 SPI 速度

当初、Atom Lite (classic ESP32) は `config.spi_fast_hz = 8000000` に落としていた
(全信号が GPIO マトリクス経由となるため)。AtomS3 系の 16MHz に対してレジスタアクセスが 2 倍遅い。

その後、classic ESP32 と ESP32-S3 の両方を 20MHz に設定した
([src/common/hw_pins.h](../src/common/hw_pins.h) の `UWB_SPI_FAST_HZ`)。GPIO マトリクス経由の全二重転送の上限が
20MHz で、80MHz の APB クロックを割り切れる値でもある。起動時に 20MHz で ID レジスタを読み戻し、Atom Lite と
Atom Matrix の起動ログでも読み戻しが通ることを確認していた。

ところが、この設定は実際には効いていなかった。ライブラリは `spi_fast_hz` を受け取るが、初期化の途中で
高速レートへ切り替える処理を呼んでおらず、すべての転送を初期化時の `spi_slow_hz` (2MHz) で行っていた
(Qorvo のドライバが切り替えを呼ぶのは、このライブラリが使っていない初期化経路だけだった)。
起動時の読み戻しも 2MHz で行われていたので、何も確かめていなかった。8MHz に落としたときも
20MHz に上げたときも、実際の速度は同じ 2MHz である。

フォークで `dwt_initialise()` の直後に `spi_fast_hz` へ切り替えるように直した。レジスタ 1 回の読み書きは
約 39 µs から約 17 µs になった (5.2)。あわせて次のようにした。

- 起動時の読み戻しは 1 回ではなく 64 回続けて行う。タイミングの際では失敗がときどきしか出ないため
- 読み戻しに失敗したら 10MHz、それも駄目なら 2MHz で初期化し直す
  ([uwb_link.cpp](../src/common/uwb_link.cpp) の `initUwbWithFallback()`)。2MHz はこれまで実際に動いていた速度で、
  少なくとも従来より悪くはならない

AtomS3R のタグでは 20MHz で読み戻しが通り、10Hz で 4 台 × 1140 回の測距を失敗 2 回 (`RX_ERROR`) で終えた。
アンカーは AtomS3 (2 台)、AtomS3 Lite、Atom Matrix のいずれも 20MHz で読み戻しが通り、30Hz まで測距できた。
Atom Lite は実際に 20MHz で動かしての確認をまだしていない。以前の確認は 2MHz での動作確認として読む。

- Atom Lite: 以前からアンカーとして運用しており、タグとしても動作することを確認した (2MHz)
- Atom Matrix: タグとアンカーの両方で動作することを確認した (2MHz)。アンカーは 20MHz でも確認した

AtomS3 Lite のアンカー (0x0102) だけ、`responseTxDelayUus` を 1000 にすると `TX_START_FAILED` が 8 割近く出た。
余裕は -257〜-139 µs で、Poll の受信の検知が最大 1 tick 遅れていた。IRQ 線 (G39) を読むと、割り込みを
すべて禁止しても High のままで、内部プルダウンを付けると Low になった。QM33120 が線を駆動しておらず、
つながっていない。拡大写真ではんだ付けに隙間が見つかった。IRQ 待ちのフォークは IRQ が来なくても 1 tick の
タイムアウトで回り続けるので、3000 の余裕では失敗にならず、これまで気付かなかった。はんだを直すまでは、
この 1 台を `-D M5STAMP_UWB_WAIT_MODE=1` (IRQ を使わず SYS_STATUS を読み続ける) でビルドして動かしている。
その場合の余裕は 726〜743 µs で、IRQ 待ちの AtomS3 と変わらない。

### 5.4 同時性誤差

4 台巡回に 26ms かかるため、最初と最後の測距で時刻が 26ms ずれる。
ローバーが 1m/s で走行する場合 2.6cm のズレとなる。この速度域では無視してよいが、
高速走行させる場合は効いてくる。FC の慣性情報で補間することで吸収できる。

### 5.5 結論

- **10Hz は確実に達成できる**。タグの既定の周期は 100ms (10Hz) にした
  ([main_tag.cpp](../src/main_tag.cpp) の `UWB_RANGE_CYCLE_MS`。ビルドフラグで変えられる)
- **30Hz は理論上ギリギリ届くが、現状の config のままでは不可能**。5.2 のパラメータ削減が前提
- 5.2 の削減を入れた結果、アンカー 4 台で **30Hz まで失敗なく測距できた**。1 測距 3ms、4 台巡回 12ms。
  30Hz ではタグの LCD の書き換えで周期が最大 3ms 揺れる (5.2 の「シリアルログ」)
- 現実的には **10〜20Hz** を測位レートとし、FC 側の IMU/EKF で高レートに補間する構成を推奨
- UWB のレートを限界まで追うより、FC 側で慣性を積分し UWB で補正する方が滑らかで外れ値にも強い。
  UWB 測距が 1 周期落ちても位置推定を継続できる

まず現状のタグで `elapsedMs` の実測値を確認する。既にログに出力されているため、
1 測距の実時間が 6.5ms 前後に収まっているかを見れば、30Hz が射程かどうか判断できる。

## 6. IMU の扱い

Atom 内蔵 IMU は**使用しない**。ローバーにフライトコントローラを搭載しており、IMU はそちら側を使う。

参考: 現状のスケッチでは `cfg.internal_imu = false` としている。内部 I2C バスが UWB の RST / IRQ と
同じピンを使用するためであり、この設定は維持する。IMU をタグ側 Atom で使う必要がないため、
ピン競合の解決は不要となった。

タグ Atom と FC 間のインターフェース (UART / I2C / CAN 等) は別途検討する。

## 7. サーバー連携 (Wi-Fi)

### 7.1 データフロー

1. タグ起動 → Wi-Fi 接続
2. サーバーからアンカー座標表とバイアス補正値を取得 (HTTP/JSON を想定)
3. 取得したデータを NVS にキャッシュ
4. 以降の測位ループは Atom 内で完結。Wi-Fi が切断されても測位は継続
5. 走行中は測距結果と推定位置をサーバーへ送り続ける (デバッグ用のテレメトリ。UDP)

測位の計算自体はサーバーに依存しない。テレメトリが届かなくても走行には影響しない。

### 7.2 取得するデータ

```json
{
  "rev": 7,
  "pan_id": "0xDECA",
  "bias_mm": 0,
  "anchors": [
    { "id": "0x0100", "x": 0.000, "y": 0.000, "z": 1.800 },
    { "id": "0x0101", "x": 5.120, "y": 0.000, "z": 1.800 },
    { "id": "0x0102", "x": 5.080, "y": 4.310, "z": 1.800 },
    { "id": "0x0103", "x": 0.030, "y": 4.290, "z": 1.800 }
  ]
}
```

`id` は 2.2 の採番どおり UWB の `responderAddress` そのものである。アドレスを別フィールドに分けると
二重管理になるため持たせない。

サーバー側の詳細 (エンドポイント、データベース、テレメトリの受信) は
[server-design.md](server-design.md) にまとめる。本節は**タグから見た取得内容**のみを扱う。

### 7.3 NVS キャッシュの必要性

サーバーが落ちている、あるいは Wi-Fi が繋がらない状態でもローバーを動かせるようにするため、
取得済みの座標表は NVS に保存する。起動時はまずサーバーへ問い合わせ、失敗したらキャッシュにフォールバックする。
キャッシュも無い場合のみ測位不能として扱う。

### 7.4 Wi-Fi と UWB の同時動作 — 要検証

ESP32 の Wi-Fi タスクは比較的高い優先度で動作し、CPU を占有する時間帯がある。
一方 `respondDSRange()` / `requestDSRange()` の待機ループは `delay(1)` でポーリングしている
(`receiveFrame()` の実装と同様の構造)。

DS-TWR のフレーム送信タイミング自体は QM33120 チップ内部でハードウェア的にスケジュールされるため、
ホスト側の遅延がただちに測距精度を壊すわけではない。しかし、

- ホストのポーリングが Wi-Fi タスクに阻害され、受信完了の検出が遅れる
- 結果として `hostTimeoutMs` に達し、測距失敗としてカウントされる

という経路で**測位レートに影響する可能性がある**。

#### 方針: Wi-Fi は常時接続とする (決定)

デバッグのためにテレメトリを継続送信するため、**走行中も Wi-Fi は切らない**。
「座標表の取得後に `WiFi.mode(WIFI_OFF)` する」案は採らない。テレメトリが取れなくなり、
可視化による精度評価が成立しないためである。

そのうえで、レートへの影響は以下で抑え込む。詳細は [server-design.md](server-design.md) の 7.1 に書く。

- UWB 測距タスクを Core 1 に固定する (ESP32-S3 はデュアルコア。Wi-Fi は通常 Core 0)
- 送信は複数サイクルをまとめて UDP 1 発にし、巡回の先頭スロット直前に行う。測距と測距の間に割り込ませない
- Wi-Fi の再接続処理で測位ループをブロックしない

影響の大きさは実測で確認する。許容できない場合でも Wi-Fi を切るのではなく、
送信頻度を下げる方向で調整する。

## 参考: 確認済みのライブラリ挙動

`m5stack/M5Stamp-UWB` について、本検討にあたり確認した事項。

- `respondDSRange()` は `dst != responderAddress` のフレームを破棄する。ブロードキャスト受信は非対応。
  Poll 待ちで破棄した場合も受信は続けず、`RangeFrameMismatch` を返す。このとき `txMarginUs` は未設定のまま
- `receiveFrame()` はアドレスフィルタを行わない。`src` / `dst` は `M5Stamp_UWBRxResult` として返る
- `M5Stamp_UWBFrameConfig.dst` のデフォルトは `0xFFFF` (ブロードキャスト)
- `requestDSRange()` / `respondDSRange()` は config を引数で受け取り、内部に役割状態を持たない。
  同一機体で initiator / responder を動的に切り替え可能
- `M5Stamp_UWBDSResponderResult.requester` には Poll 送信元アドレスが入る。
  Poll 未受信時は 0 のままで、非ゼロなら Poll/Response は成立して Final が失われたことを意味する
- SYS_STATUS のポーリングは、読み出しの間に `delay(1)` を挟む。受信の検知が次の FreeRTOS tick まで遅れる
  (次節)
- 遅延送信の成否は、`dwt_starttx()` が開始コマンドの直後に SYS_STATUS の HPDWARN を読んで判定する。
  ライブラリは HPDWARN をクリアしないが、次の交信には残らない (失敗直後の 1018 回すべてで確認)

## 参考: M5Stamp-UWB のフォーク

ライブラリは上流の `m5stack/M5Stamp-UWB` ではなく、フォーク
[8ga3/M5Stamp-UWB](https://github.com/8ga3/M5Stamp-UWB) の `irq-wait` ブランチを、コミットで固定して使う
([platformio.ini](../platformio.ini) の `lib_deps`)。2026-09-27 に切り替えた。

### 経緯

アンカー 1〜4 台のどの構成でも、タグの測距が `TX_START_FAILED` で約 17% 失敗していた。
失敗していたのは Final の遅延送信 (`dwt_starttx(DWT_START_TX_DELAYED)`) である。

- Final は、Response の受信時刻から `finalTxDelayUus` (1800 uus) 後に送信するよう予約する
- 上流は受信完了を `delay(1)` を挟んだポーリングで待つため、受信の検知が次の FreeRTOS tick まで遅れる
- 検知から予約までの SPI 転送に約 900 µs かかり、予約は送信時刻の約 200 µs 前までに済ませる必要がある。
  これに tick 待ちの遅れ (最大 1 ms) が加わると間に合わない
- 遅れの大きさは、交信と tick の位相で決まる。タグは `millis()` の区切りで測距を始めるので、位相は
  `millis()` と tick の位相差、つまり起動にかかる時間で決まる。同じバイナリなら再起動しても変わらない。
  そのため、測距と関係のない変更でも失敗率が 0% から 100% の間で振れた

### 検証

測距の開始を 0〜900 µs の範囲で 100 µs ずつずらし、各段階で 200 回ずつ試行した
(AtomS3 のタグ、アンカー 4 台、`finalTxDelayUus` = 1800)。余裕時間は、遅延送信を予約した時点で
送信時刻まで残っていた時間である。

| 待ち方 | 余裕時間 | 失敗 |
| --- | --- | --- |
| `delay(1)` (上流) | -237〜944 µs。開始のずれに対して周期 1 ms で変わる | 段階により 0〜100% |
| IRQ 割り込み (フォーク) | 705〜947 µs。開始のずれによらずほぼ一定 | 2400 回中 0 回 |

`delay(1)` で失敗した 1018 回の余裕時間は最大 202 µs で、約 200 µs が成否の境目になる。
プリアンブルと SFD の送信時間 (約 136 µs) に、予約後の SPI 転送の時間を足した値と合う。

### フォークの変更点

- `M5STAMP_UWB_WAIT_MODE` で待ち方を選ぶ (0 = `delay(1)`、1 = busy-poll、2 = IRQ。既定は 2)。
  2 は RXFCG・RX タイムアウト・RX エラーだけを IRQ ピンへ出し、ISR からのタスク通知で起きる。
  TXFRS を含めないのは、Poll の送信完了から Response の処理まで立ったままになり、RXFCG の立ち上がりを
  取りこぼすためである。通知の待ちは 1 tick でタイムアウトするので、取りこぼしても上流と同じ遅れで済む
- DS-TWR の結果に `txMarginUs` (上記の余裕時間) を加えた。タグでは Final、アンカーでは Response の値になる。
  `M5STAMP_UWB_MEASURE_MARGIN=0` を指定すると、計測のための SYS_TIME の読み出しを外せる
- `dwt_initialise()` の直後に SPI を `spi_fast_hz` へ切り替える。上流はこの切り替えをしておらず、
  すべての転送が `spi_slow_hz` (2MHz) で行われていた (5.3)
- SPI の転送を 1 バイトずつの `transfer()` から、最大 64 バイトずつの `transferBytes()` / `writeBytes()` に
  まとめた。Arduino-ESP32 のこれらの関数はバッファを 32 ビット単位で読み書きするので、4 バイト境界に
  揃えた作業用バッファを経由する

ファームウェアは、余裕時間の最小値を `DS_RANGE_STAT` / `DS_RESP_STAT` の `min_margin_us` に、失敗時の値を
`DS_RANGE_FAIL` の `margin_us` に出力する。起動時の `UWB_TIMING` で `finalTxDelayUus` と待ち方を確認できる
([src/common/uwb_link.cpp](../src/common/uwb_link.cpp))。

### 未確認の事項と今後

- 約 900 µs の処理時間の大半は SPI 転送である。ラッパーは 1 バイトごとに `transfer()` を呼び、転送ごとに
  `beginTransaction` と CS の `digitalWrite` を行っている。まとめ転送にすれば縮み、`finalTxDelayUus` を下げられる。
  まとめ転送と 20MHz への切り替えで約 400〜450 µs になり、`finalTxDelayUus` は 1200 に下げた (5.2)
